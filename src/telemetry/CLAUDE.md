# Telemetry Substrate

## Purpose

The OpenTelemetry substrate every instrumented seam records through: the opt-in dual-path bootstrap (`bootstrap.ts` + `sdk.ts`), the single instrumentation scope, instrument memoization, and the seconds timer (`scope.ts`), the vendored Development-status semconv constants (`semconv.ts`), the shared spec-named instruments (`instruments.ts`), the operation lifecycle (`trace-result.ts`: `startOperation` — span + duration + latched exactly-once `end()` — with `traceResultAsync` as its Result-rail adapter), the resilience-hook metric wiring (`resilience.ts`), and the per-session client connection fingerprint (`client-fingerprint.ts`). **Recording lives at the seams** (the kernel tool/resource wrappers, the sync driver, the clients, the notifier, the transports' `initialize` handshake) — this directory only provides the shared vocabulary and lifecycle.

## Sharp edges

- **Never create an instrument at module scope.** The metrics API has no late-binding proxy (unlike tracers): an instrument created before the SDK registers the global MeterProvider is a no-op FOREVER. Use `lazy()` from `scope.ts` — first record always lands after SDK start in production, and tests install their provider at module scope before exercising a seam (`test/support/telemetry-test-utils.ts`'s doc-comment).
- **Nothing in the export path may touch stdout** — it is the stdio MCP wire. OTLP-only exporters; the diag logger writes to stderr (`sdk.ts` consumes `OTEL_LOG_LEVEL` _and deletes it_ so the NodeSDK can't install its stdout console logger). Never add a console exporter, even behind a flag. The diag logger's `process.stderr.write` is the third documented exception alongside `src/index.ts` and `src/transport/stdio.ts`.
- **`bootstrap.ts` must stay `src/index.ts`'s FIRST static import**, and the Dockerfile CMD must keep preloading it via `--import`. The two paths are idempotent through ESM module caching; only the `--import` path makes the ESM loader hook effective, so **a module-patching instrumentation added to `sdk.ts` silently does nothing under the npm-bin/stdio path** — catch that in review (ADR-0018 records the trade).
- **`semconv.ts` is vendored on purpose** — the package's `incubating` entry point breaks in minor versions. The MCP/GenAI conventions are Development-status (pinned at spec v1.39.0): when they stabilize, this file is the single rename site. Custom names take the `mcp_paprika.` prefix; never coin new `mcp.*`/`gen_ai.*` names the spec doesn't define.
- **Attribute discipline**: no identity/credential VALUES (emails, subs, tokens — the `REDACT_PATHS` key list is the reference) on any attribute WE set, ever. Cardinality is the SEPARATE axis: a high-cardinality value (a UID, a full URI) must never label a METRIC, but it is fine on a SPAN attribute — traces are per-span, so `mcp_paprika.resource.uri` carries the full URI for debugging while the duration histogram keeps only method + kind. The conformance test (`test/conformance/telemetry-attributes.test.ts`) gates custom-attribute KEY NAMES (no credential/identity terminal segment like `email`/`token`/`sub`); attribute VALUES are review + per-seam-test territory. URL attributes the AUTO-instrumentations set themselves (`url.full`, `url.query`) are scrubbed at the trace-exporter chokepoint (`url-scrub.ts` — neither library offers a sanitization hook); a new instrumentation inherits the scrub for free, but a NEW URL-shaped attribute key needs adding to `URL_ATTRIBUTE_KEYS` there.
- **Telemetry must never alter behavior.** `traceResultAsync` passes both Result arms through unchanged; the tool/resource wrappers are throw-transparent (their rethrows are pinned in the ADR-0014 conformance gate); recording inside never-throws contracts (notifier, index events) relies on OTel API calls not throwing — don't wrap recording in logic that can.

- **The client fingerprint is captured once per session and READ at call time, never threaded.** `recordClientConnection` (each transport's `oninitialized`) records a POINT-IN-TIME `mcp_paprika.client.connect` span with the FULL capability tree (high detail a metric label can't hold), increments `mcp_paprika.client.connections` with the cardinality-bounded census slice only (name + major version + transport), and stashes the fingerprint in a per-server `WeakMap`. The kernel tool wrapper reads it via `clientAttrs(ctx.server.server)` to tag each `tools/call` span — so the fingerprint never plumbs through `DomainCtx`. The connect span is point-in-time on purpose: a session-lifetime span never exports until close (under stdio, the whole process) — the same anti-pattern the HTTP `GET /mcp` SSE exclusion avoids. `clientInfo` is the client APP identity (not the OAuth user) — no PII/token rides on it, and only name/major/transport ever label a metric. The negotiated protocol version is NOT retained server-side (`setProtocolVersion` is client-only), AND the SDK's `ClientCapabilities` schema STRIPS every key it doesn't model — including the top-level `extensions` map where the apps/widget capability (`io.modelcontextprotocol/ui`) lives — so each transport sources the REQUESTED protocol version AND the RAW capabilities itself (HTTP from the parsed initialize body; stdio from a post-connect `onmessage` sniff). The connect log carries the raw capability tree verbatim; the span derives bounded scalars (`cap.ui`, `cap.extensions`, …) from it. Don't "simplify" the fingerprint to read `getClientCapabilities()` — that silently loses the apps axis.
