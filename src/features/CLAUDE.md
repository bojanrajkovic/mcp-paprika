# Feature Implementations

## Purpose

Three feature modules on the kernel — kernel modules that are optional features, not data domains. `discover/` (semantic search) and `photo-gen/` (AI photos) are each composed in a `.state` factory and opt-in on config: the semantic-search stack (`EmbeddingClient` → `VectorStore` → the owned `JsonVectorIndex`) and the photo-generation stack (`PhotographyClient` + SSRF-hardened image fetch). An unconfigured feature builds a `null` component; the kernel registers their tools (`discover_recipes`, `generate_recipe_photo`) **unconditionally**, and the feature gate lives inside the handler, which no-ops when its component is `null` (ADR-0009 §5).

`widgets/` is the odd one out: it owns no entity and reads no config, registers **no tool**, and serves the prebuilt `ui://widget/{name}` HTML resources a host renders in a sandboxed iframe (ADR-0019). Its sharp edges (the build-time-only toolchain, the boot-degrade, the path resolution) live in its own `CLAUDE.md`.

## Sharp edges

**Norm is a cache, never trusted (`JsonVectorIndex`).** The per-item norm is recomputed from the vector on every upsert and on every load; the persisted value is discarded. A changed vector can never leave a stale norm behind: this directly closes a ranking-corruption bug in the `vectra` package's upsert path that the owned index replaces. The on-disk format is a `vectra` subset, purely so existing indexes load with no re-embed migration; the legacy norm field rides along but is always recomputed. (ADR-0003.)

**Corruption routes to recovery, not to `NaN` scores.** Vectors must be non-empty, all-finite, and share one dimension; zero-norm vectors are rejected on insert AND on load. Violations `err` (treated as corruption / programmer error, the index being owned code — ADR-0014) and surface to `VectorStore`'s recovery path (backup `.bak` + recreate), rather than silently producing `NaN` cosine scores. Because stored items are guaranteed positive-norm, the only non-finite score comes from a zero-norm query, guarded once up front, not per item.

**Total ordering, ties broken by id.** Query results sort by descending score with ties broken deterministically by id ascending; never the `NaN`-tolerant sort `vectra` performed. Don't "optimize" the comparator into a partial order; the determinism is the point (also recorded in ADR-0003).

**Embeddings deliberately EXCLUDE directions and nutrition.** `recipeToEmbeddingText` covers name, description, categories, ingredients, and notes only. Editing cooking steps or nutrition facts must not churn the index. If you change the text format (add/remove a field, restructure), you MUST bump `EMBEDDING_SCHEMA_VERSION` so deployed users get a full re-index on next startup; otherwise old vectors silently coexist with the new format.

**The kernel re-index seam covers what sync can't (#177).** The vector index is derived from recipes, but discover has no dependency edge into recipe — so recipe writes (`commitRecipe` / `commitRecipeHardDelete`) and category writes (`commitCategoryUpsert`) emit `recipe-changed` / `recipe-removed` / `category-changed` on `infra.indexEvents`, and discover's `index` boot hook subscribes and re-embeds. This is NOT redundant with sync-driven indexing: a tool-written recipe's UID is pending, so the sync recipe-diff filters it out — without the seam a tool-created recipe is never embedded and a tool-edited one keeps its stale vector. A category's display name is baked into its recipes' embedding text, yet an app-side or tool-side rename changes no recipe hash, so the recipe sync never re-fetches them; the `category-changed` handler re-embeds the affected recipes explicitly. Emits are fire-and-forget and never throw — a re-index failure must not break a sync cycle or a tool write — and the `VectorStore` serializes its writes via an internal mutex, so unawaited concurrent emits are safe.

**The `index` boot hook self-heals down-time changes and latches a retry on a startup outage (#177).** discover's `index` hook runs AFTER the initial `syncOnce()` (the boot pipeline guarantees it), so the recipe and category stores are already warm and category names resolve through the recipe contract (`ctx.deps.recipe.resolveCategoryNames`). Its startup reconcile re-embeds whatever drifted while the server was down — notably a category rename, which changes no recipe hash, so the recipe diff never re-fetches it and the initial `syncOnce()` fired its re-index events before this subscription existed. The reconcile is best-effort: a transient embeddings outage at startup latches `reconcilePending`, which the next `recipe-changed` cycle drains, so a recovered backend self-heals without a recipe edit or restart.

**Photo egress is SSRF-hardened (deliberately not an ADR, but a real threat-model decision; see `../shared/photo-fetch.ts`).** Any server-side image fetch (the `upload_recipe_photo` `url` source AND `generate_recipe_photo`'s restyle path that fetches a recipe's `photoUrl`) goes through `fetchImageBytes`, never a raw `fetch`. The guard is layered: an `ipaddr.js` unicast-only check rejects any IP literal that isn't public (loopback / private / link-local / CGNAT / IPv4-mapped-IPv6, etc.), AND a DNS-rebinding-safe undici `Agent` whose connector resolves through `ssrfLookup`, so the SAME resolved address is validated and connected, closing the TOCTOU gap a separate pre-check-then-fetch would leave open. Redirects are blocked (`redirect: "error"`) because a redirect-to-private is a bypass. Two non-obvious constraints: it must import `fetch` from **undici**, not Node's global `fetch` (the dispatcher is an `Agent` from this undici copy, and the global fetch's bundled undici has an incompatible handler interface: `UND_ERR_INVALID_ARG`); and `upload_recipe_photo` deliberately exposes **no `file_path`** source, because a server-side path read would be an LFI/SSRF vector and is meaningless for the remote HTTP transport. Photos come only from a vetted URL, a generated-image token, or inline normalized bytes.

**Generated-photo previews evict-oldest, not reject-on-full (`GeneratedImageStore`).** Unlike the auth TTL stores (where evicting an in-flight entry is an attack vector), dropping a stale throwaway preview is harmless, so the ring buffer overwrites the oldest when full. Single-use and race-safe: `upload_recipe_photo` `consume`s the token (synchronous delete before any `await`, so two concurrent calls can't both attach the same preview), then `restore`s it ONLY on a pure-validation failure (wrong `recipe_uid`, before any write). It must NOT restore after `attachPhotoToRecipe`, which uploads to Paprika before the local commit; restoring there could let a retry duplicate an already-uploaded photo. A validated-but-failed attach loses the preview (regenerate); that's the duplicate-safe trade.

**The resilient clients are `Result`-native; the cockatiel internals still throw.** `EmbeddingClient.embedBatch`/`embed`, `PhotographyClient.generate`, and every `VectorStore` operation return `ResultAsync` (ADR-0014): a breaker-open errs as `CircuitOpenError` (from `utils/errors.js`, shared with `PaprikaClient`), a permanent HTTP failure as the client's `*APIError`, and a foreign escape (malformed body, abort) wraps as the client's base error with its message preserved. Only the cockatiel-governed `execute` closures keep throw-based control flow (form #3, pinned in the conformance test) — the throw protocol ends at each client's `fromPromise` edge. `VectorStore` writes are serialized via a per-instance `async-mutex`: it is a process-wide singleton with concurrent writers (the index-event seam on `infra` fires the recipe and category-change handlers without awaiting them), and the index's begin/end transaction plus the shared hash map can't tolerate overlapping writes (#177).
