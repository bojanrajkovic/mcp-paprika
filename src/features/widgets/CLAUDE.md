# Widgets Feature

## Purpose

The kernel module that serves the interactive widget surface (ADR-0019): it registers the `ui://widget/{name}` resource and serves prebuilt, self-contained HTML for a host to render in a sandboxed iframe. It owns no Paprika entity, reads no config, and exposes `EmptyApi`. A tool opts a result into a widget by declaring `ToolSpec.ui.resourceUri` (the kernel maps it onto `_meta`); this module is the other half — the resource that URI points at. It registers ONE tool: `record_widget_timing`, the **app-only** (`ui.visibility: ["app"]`) render-timing sink — callable by a widget via `callServerTool`, hidden from the model's `tools/list`.

Canonical home: `docs/architecture.md` ("Widget surface") + [ADR-0019](../../../docs/adr/0019-mcp-app-widget-surface.md). The build pipeline lives in `scripts/build-widgets.ts`; the dev preview in `src/transport/widget-preview.ts`. The **visual design system** — shared with the OAuth consent screen — is the root `/PRODUCT.md` (strategic register), `/DESIGN.md` (Stitch-format visual system), and `/.impeccable/design.json` (machine-readable sidecar).

## Sharp edges

- **`esbuild`, `esbuild-svelte`, `svelte`, and `@modelcontextprotocol/ext-apps` are BUILD-TIME-only devDependencies — nothing on the NODE runtime path may import them.** A widget's HTML and the shared `vendor-<hash>.js` are built by `scripts/build-widgets.ts`; the Node server only ever reads those as bytes. ext-apps is now a **value** import (`import { App, applyHostStyleVariables, … }`) — but ONLY in the browser bundles esbuild compiles (`mount-widget.ts`, `shared/host-style.ts`), which are excluded from the Node `tsc` graph and resolved at runtime by the import map (ADR-0025), so the value import never reaches `dist/`'s Node tree. The Node-side files (`artifacts.ts`, `module.ts`, `resources/widgets-resource.ts`, `transport/widget-preview.ts`, `transport/widget-vendor.ts`) reference ext-apps only as a **string** (the import-map specifier) or **type-only** (the preview shim's `SHIMMED_*` pins) — never a value import. A value import in any Node-side file reaches `dist/` and crashes the prod container (`pnpm install --prod` omits ext-apps); the `prod-widgets` CI job (`scripts/verify-prod-widgets.mjs`) is the hard gate — it now asserts each widget HTML EXTERNALIZES the runtime (a bare import, never an inlined `globalThis.ExtApps`) and that exactly one `vendor-<hash>.js` (+ `.gz`/`.br`) was built. esbuild-svelte's default export is non-callable under nodenext (dual CJS/ESM, no `exports` map), so the build loads it via `require` and recovers the factory type.
- **The ext-apps runtime is EXTERNALIZED, served transport-conditionally (ADR-0025).** `build-widgets.ts` emits ONE content-hashed, brotli/gzip-pre-compressed `vendor-<hash>.js` (ext-apps' `app-with-deps` verbatim); each widget bundle is ESM (not IIFE — the IIFE existed only to scope names against the old inlined runtime in one shared `<script>`) with a bare `@modelcontextprotocol/ext-apps` import esbuild keeps `external`, fully minified (env-gated: `MCP_WIDGETS_DEBUG=1` and `pnpm dev:widgets`/`--watch` keep it readable). The serving layer fills `WIDGET_VENDOR_SLOT` with the import map: over **HTTP** (`config.oauth.publicUrl` set) it points at `{origin}/widgets/vendor-<hash>.js` (served by `transport/widget-vendor.ts`, unauthenticated + `immutable` + `Vary: Accept-Encoding` + CORS, mounted before the `/mcp` bearer guard) and emits `_meta.ui.csp.resourceDomains=[origin]` on the served content item so the host allowlists it for `script-src` (`csp` is RESOURCE meta — `McpUiToolMeta.csp` is `never`); over **stdio** (no public URL, no HTTP server) it inlines the vendor as a `data:text/javascript;base64,…` module (self-contained, offline). `loadVendorImportMap` (state) and `loadVendorBytes` (the HTTP route) both live in `artifacts.ts`. Don't reintroduce a "self-contained, fetches nothing" assertion — externalization is the point now.
- **A missing or empty `dist/widgets` DEGRADES (warn + empty map), it does not throw.** The kernel constructs every module regardless of transport, so a hard failure at construction would brick the stdio transport and any `pnpm dev` that has not built widgets. The hard "widgets exist and serve" assertion lives in CI, not at boot. Run `pnpm build:widgets` (or `pnpm dev:widgets` to watch) to populate it locally.
- **One `import.meta.url`-relative path resolves `dist/widgets` from BOTH layouts** (`artifacts.ts`): the built `dist/features/widgets/` and the tsx dev run from `src/features/widgets/` both sit three levels below the repo root, so `../../..` is the root either way and the built widgets always live at `<root>/dist/widgets`. Don't "simplify" to a sibling lookup — it breaks the dev run.
- **Widget browser source is excluded from the two NODE-side tsconfigs but typechecked by `svelte-check`.** A widget's `main.ts` imports its `.svelte` component and uses browser globals, so it is compiled by esbuild and excluded from `tsconfig.json` / `tsconfig.test.json` (`tsc` can't parse `.svelte` and would apply the Node `lib`). Instead `tsconfig.widgets.json` _includes_ exactly those browser entries — `mount-widget.ts`, `*/main.ts`, `**/*.svelte` — with a browser `lib` (DOM) and `types: []`, and `svelte-check` checks them; `pnpm typecheck` chains `typecheck:widgets`, so the pre-push hook and CI cover it. The node-side exclude stays scoped to the browser entries, NOT the whole per-widget subtree: the module and resource files, and the widget feature's tests, stay on `tsc`. (An earlier broad subtree glob silently dropped the test files from typecheck — don't reintroduce it.) A widget with a browser `.ts` beyond `main.ts` must be added to BOTH the node-side excludes AND the `tsconfig.widgets.json` include — otherwise `tsc` tries to compile it (and fails on the `.svelte`/DOM globals) and `svelte-check` never covers it. `svelte-check` runs with `--fail-on-warnings`, matching `oxlint --deny-warnings`: an a11y / unused-CSS / type warning fails the gate, so suppress a deliberate one with a documented `<!-- svelte-ignore … -->`.
- **Widget components use `<script lang="ts">`, but only TYPE-only TypeScript.** Svelte 5 strips type-only syntax (annotations, `import type`, generics, `interface`, `as`/`satisfies`) natively, so the esbuild pipeline needs no preprocessor — `scripts/build-widgets.ts` runs the `esbuild-svelte` plugin (the Svelte 5 compiler) with no `preprocess` option. Non-erasable TS (enums, constructor parameter-properties, decorators) would need a `svelte-preprocess`/`vitePreprocess` step that isn't wired; don't use those features in a widget. The ext-apps `App` type is imported TYPE-only (`import type { App }`) — erased, so ext-apps stays a build-time-only devDependency (the same pattern `transport/widget-preview.ts` uses) while typing every `app.*` bridge call.
- **A list-rendering widget must use a keyed `{#each items (item.uid)}`.** Svelte then updates rows in place, so the scroll position survives a re-render and `animate:flip` can animate a reorder (e.g. a checked item sinking to the bottom of its aisle group). A non-keyed each — or a full `innerHTML` rebuild — recreates the list and resets the scroll. The grocery checklist depends on both.
- **Svelte 5 has no `bind:scrollTop` element binding** (only `bind:scrollX`/`scrollY` on `<svelte:window>`), and it compiles in neither esbuild nor `svelte-check` — the build fails outright. So a widget that must keep a scroll position across a view swap **keeps the scrolling view mounted** rather than restoring an offset: the recipe-browser leaves its browse list in the DOM and `display:none`s it (`.browse.hidden`) while the detail pane shows, so the scroll position **and** every already-loaded `RecipeThumb` survive the swap with no `el.scrollTop` save/restore dance (the Back re-fetches nothing). Reach for keep-mounted before a `bind:this` + mount-time `use:` restore action. Rows carry `content-visibility: auto` + a `contain-intrinsic-size` estimate so off-screen rows skip layout/paint (the cheap long-list win short of virtualization).
- **The recipe-browser morphs its browse ↔ detail swap with the View Transitions API** (`swapView` wraps the `detail` mutation in `document.startViewTransition`, flushing Svelte's pending DOM with `await tick()` inside the callback). Two gotchas: the shared-element `view-transition-name` (`rb-recipe-title`) must stay **unique per snapshot**, so only the _open_ row's title carries it and `RecipeDetail` only names its heading when a consumer passes the opt-in `titleTransitionName` prop (menu and meal-week omit it → inert; the meal-week planner uses a directional root push via `dirAttr` instead — a title morph from a 12.5px board cell to the 19px heading read as a blurry bitmap stretch). And it's a JS API, not a CSS transition, so it's gated in JS on `reduced` — `startViewTransition` is skipped under reduced motion / where the API is absent (Firefox), falling back to the plain swap. Verify the swap under the `/widget-preview` shim.
- **The widget-wide focus ring and CSS reduced-motion live once in `WidgetShell`, not per widget.** WidgetShell defines `main :global(:focus-visible)` (2px `--accent` ring, offset 2px — the DESIGN.md focus spec) and a global `@media (prefers-reduced-motion: reduce)` block that zeroes CSS animation/transition durations across every descendant. Don't re-declare either in a widget. A control overrides only `outline-offset` for an inset ring on a full-bleed row (so the outset ring isn't clipped at the row's edge); its scoped local `:focus-visible` outspecifies the low-specificity global. A component that needs a NON-duration reduced-motion reset (grocery's `.tick { stroke-dashoffset: 0 }`) keeps a small local `@media` block for just that. **Svelte JS transitions (`slide`/`fly`/`animate:flip`) are NOT CSS and slip past the `@media` block** — gate their durations in JS via `shared/motion.ts` (`motion(N)` / `reduced`), as the pantry's subtractive remove and the checklists' `animate:flip` do.
- **The pantry's touch rows carry a visually-hidden `.sr-action` button. It IS the assistive-tech path.** On a touch host the visible Out button is replaced by the swipe, so each row keeps a clipped-away real button a screen reader can activate (revealed as a pill on hardware-keyboard focus). Don't prune it as unused. Related: the pantry's drawer subtree uses **no Svelte transitions** — presence/open-close are pure-CSS collapses and the row move is a hand-rolled WAAPI clone flight with timeout cleanup — because a Svelte outro removes its element only when its animation finishes, so a frozen document timeline (a backgrounded host tab, the headless preview) strands invisible ghost rows whose buttons stay in the AT tree; the deferred crossfade also has open multi-item issues (sveltejs/svelte#10252/#11372/#13977). Don't reintroduce `transition:`/`animate:` inside the drawer.
- **The `ui://` URI a tool references and the resource registered here must match exactly**, and `{name}` must have a `src/features/widgets/{name}/` source dir — pinned by `test/conformance/widget-ui-references.test.ts`. The resource `list` enumerates the in-memory artifact map loaded at construction, never the directory per request.
- **`.svelte` is linted AND formatted, by two tools that never overlap.** oxlint parses a widget's `<script>` block and applies the repo rules (so widget scripts are covered by `pnpm lint` and the pre-commit hook); oxfmt does **not** recognize `.svelte`, so `prettier` + `prettier-plugin-svelte` format widget markup/styles instead — the `format:svelte` / `format:svelte:check` scripts (chained into `format` / `format:check`) and a `prettier-svelte` pre-commit command, all globbed strictly to `*.svelte`. The split is deliberate: oxfmt owns `.ts`/`.json`/`.md`, prettier owns `.svelte`, and the two never claim the same file. There is **no discoverable prettier config** — the scripts and hook pass `--plugin prettier-plugin-svelte` explicitly — so an editor's Prettier extension can't quietly take over `.ts` and fight oxfmt.
- **`WidgetShell` sizes to content on short widgets, capped at the host's container height on long ones.** `main` uses `min-height: 10rem` (a floor so the body reports a usable height to the host's autoResize even when the iframe starts small) and `max-height: var(--widget-max-h, none)` — the cap is the host-provided container height (see the next edge), NOT a fixed height. A scroll region (`GroupedList`'s `.scroll`, the meal planner's `SlotPane` / `RecipeDetail`) carries `flex: 1; min-height: 0; overflow-y: auto` and scrolls only once `main` hits the cap; chrome rows are `flex: none` so only the scroll region absorbs the overflow. Don't "simplify" `max-height` to `height: 100%`.
- **The viewport cap is the HOST's container height (`--widget-max-h`), never `100dvh` — the iframe-relative unit deadlocks the autoResize.** ext-apps autoResize measures `document.documentElement` forced to `height: max-content` (`app.js` `setupSizeChangedNotifications`). Inside the iframe `100dvh` resolves to the CURRENT iframe height, so when the host starts the iframe small, `max-height: 100dvh` + an internal scroll caps that measurement at the small height and the widget never grows past the `min-height` floor (the trap the floor only half-breaks). `host-style.ts` instead sets `--widget-max-h` from `hostContext.containerDimensions` (a STABLE px height), so the scroll region caps at the real screen and the autoResize can still grow the iframe up to it. No `containerDimensions` → `--widget-max-h` unset → no cap (`none`): the widget grows to content and the host page scrolls. Never reintroduce `100dvh` (or any `vh`/`dvh`) as the cap.
- **Browser test files in `shared/` are excluded from node tsc but run in vitest.** `host-bridge.test.ts` and `host-style.test.ts` live alongside the source they test; they're typechecked by `tsconfig.widgets.json` (browser lib) via the same `shared/` directory-glob include that covers the source files. Use explicit vitest imports (`import { describe, it, expect, vi } from "vitest"`) — the widget tsconfig has `types: []` so vitest globals are not auto-injected. For DOM-calling code (`host-style.ts`), stub `document` with `vi.stubGlobal` and restore with `vi.unstubAllGlobals()` in `afterEach`. The test harness factory (`test/support/widget-ext-app.ts`) creates duck-typed fake `App` objects; the ext-apps style helpers are real value imports now (ADR-0025), so a test asserting them `vi.mock`s `@modelcontextprotocol/ext-apps` directly (as `host-style.test.ts` does) rather than installing a `globalThis.ExtApps` fake. Import the harness with a relative path from `shared/`.
- **A widget reads server capabilities from `window[SERVER_CAPS_KEY]` (injected by `widgets-resource.ts` at `resources/read` time), not from the ext-apps host context.** `renderShell` places a `WIDGET_INJECT_SLOT` comment (`<!-- __widget-inject__ -->`) immediately after `<body>`; both `widgets-resource.ts` and `widget-preview.ts` replace that literal string with their `<script>` block — no HTML parsing. The resource handler calls `supportsForm(ctx.server.server)` per-request so each client gets a snapshot of its own negotiated capabilities, serialised as JSON into `window[SERVER_CAPS_KEY]`. The grocery checklist reads it once in `onMount`: when `supportsElicitation` is true it routes "Clear N" directly to `confirmClear()` (letting the server-side `confirmGate` be the sole confirmation) and skips the inline two-tap confirm. The preview shim mirrors this in the `App` constructor from `?elicitation=1`.
- **`SHIMMED_HOST_METHODS` and `SHIMMED_EXTAPPS_HELPERS` in `widget-preview.ts` pin the preview shim surface.** The preview shim is now an **ESM module** (`PREVIEW_SHIM_MODULE`) served as the import map's `data:` URL target — the widget's `import { App, … } from "@modelcontextprotocol/ext-apps"` binds to it (ADR-0025), replacing the old `globalThis.ExtApps` classic script. `SHIMMED_HOST_METHODS` pins the `App` instance methods the shim exports against the ext-apps `App` type (a renamed method fails to compile); `SHIMMED_EXTAPPS_HELPERS` does the same for the four exported style helpers (`applyHostStyleVariables`, `applyHostFonts`, `applyDocumentTheme`, `getDocumentTheme`) `host-style.ts` imports. The preview test base64-DECODES the data-URL module from the served HTML and asserts both lists appear in it, so dropping a helper is still caught. The shim's `App` reads its sample payload off the URL **fragment** (`#payload=`, never sent in the HTTP request) into a per-page **mini-store** it mutates in place across `callServerTool` calls, so a widget's own post-action re-read reflects the action. The pin mechanics above are unchanged by either.
- **Widgets bind to the server's OWN output types, via the type-only `shared/server-types.ts` surface — they don't re-declare them.** Each widget's view-model is the server's inferred `z.infer` output type (or a `Pick`/intersection of it), so a server output-field rename is a `svelte-check` compile error here, not silent drift (pinned by intent, not a test — flip a field name in `recipe-helpers.ts` and `pnpm typecheck:widgets` fails). The re-export is **type-only** (`export type { … }`): esbuild erases the module, so no value (zod, kernel, server internals) reaches the bundle and the `prod-widgets` gate stays green. The hard constraint behind it: a widget-facing type may only be re-exported from an **import-clean leaf** (zod + branded-id leaves only — `recipe-helpers.ts`, `grocery-helpers.ts`, `menu-helpers.ts`, `pantry-helpers.ts`, `meal-schema.ts`). Re-exporting an output type from a **kernel-heavy** file (a `tools/*.ts` that imports `defineTool`, or meal's catalog-importing `tools/helpers.ts`) drags the Node-typed server graph (`paprika/client.ts`, the kernel registry) into the DOM-lib widget typecheck and **fails it** — so the four output schemas that lived in tool files (`cook`/`search`/recipe-`list`/pantry-`list`) were moved into those leaves, and meal's schemas split into `meal-schema.ts` (re-exported from `tools/helpers.ts` for the meal tools). A new widget-facing type must be reachable through such a leaf.
- **The widget guards discriminate-then-trust; they do NOT re-validate the payload field-by-field.** A buggy host is the only honest residual (a malicious host owns the iframe — re-validating its payload is theater), and only a non-array `.map` actually throws. So each `receive()`/`parse*` does: the shape discriminant (the tag field — `weekStart`, a browse `context.source`, the `uid`+`ingredients`+`directions` cluster), a `!Array.isArray(...)` spot-check on **just the arrays it iterates**, then `data as unknown as <ServerType>` and reads the typed fields straight through. Keep only the few non-type clamps that protect layout, not types: a numeric clamp a loop bound needs (cooking's `nonNegInt` prep budget, menu's `day`/`days` `Math.max`+`trunc`), a soft-read on a nested object the discriminant didn't cover (cooking's `src.prep?.…`), a documented fail-open default (pantry's `inStock !== false`), and a parse-critical format check whose failure would throw during render (the meal-week `weekStart` date-shape regex — `toIso` on an Invalid Date throws and blanks the widget). Don't reintroduce the per-field `typeof o["x"] === "string" ? … : …` ladders.
- **The dual-mode `receive()` discriminates payloads BY SHAPE.** The meal-week-planner routes the initial result, every nav re-fetch, and the inline recipe read through one `receive()` that tells a `read_meal_plan` week (`weekStart`) from a `read_recipe` slice (`uid` + `ingredients` + `directions`, via `shared/recipe-detail.ts`'s `parseRecipeDetail`). Gotcha: a new structured-output schema carrying that same field cluster would be misread — keep the discriminators distinct. The recipe read is widget-initiated, gated by the `loadingRecipeUid` token (reactive — it doubles as the per-row spinner driver): any move away (Back, week nav, day select) must null it, or a result that lands after the user left pops the detail pane over the new view. `RecipeDetail.svelte` + `recipe-detail.ts` are shared (three consumers — this widget, recipe-browse, and the menu widget); reuse them, don't re-roll the read_recipe parse.
- **`read_meal_plan` re-fetches itself for navigation** (the first widget-bearing read to do so). Prev/next pass the target week's Monday as `startDate` (the today-floor is lifted server-side so past weeks read); `navBusy` locks the arrows only on a cache miss — navigation is **cache-then-reconcile**: applied weeks are cached by `weekStart`, neighbors prefetch in the background, a cache hit swaps instantly and a silent re-read reconciles it. Gotcha: `reconcile` must re-check `week.weekStart` before applying, or a late reconcile yanks the view from a week the user already left. At ≥640px the same data renders as the `WeekBoard` (meal-type bands × day columns, swapped via a reactive `MediaQuery` — the narrow `DayStrip`+`SlotPane` master-detail below); the touch swipe pager in `SlotPane` is additive (chips stay the AT path, `touch-action: pan-y` keeps vertical scroll native). Gotcha: a no-arg `read_meal_plan` (what the assistant calls) anchors its window at today, not Monday, so a mid-week first load is a partial grid — the widget detects this (`weekStart < todayIso`) and realigns to the full week once, kept one-shot by a `primed` flag. Under the `/widget-preview` shim, `read_meal_plan` answers from its per-page mini-store, re-dating the payload's own meals into the requested window, so prev/next navigation and the one-shot realign both drive the real widget path there too; a recipe tap resolves against the payload's `meals` rows by `recipeUid` (name only — meal rows carry no nested `recipe`, so servings/time render empty).
- **The shared toolkit is in `shared/`, and `WidgetShell` is the one home of the theme tokens.** The widgets compose `WidgetShell` / `GroupedList` / `ItemRow` / `PillButton` / `Toast` / `StatusScreen` / `BrandMark` / `Spinner` plus the `host-bridge.ts` / `host-style.ts` / `motion.ts` / `group.ts` helpers; only the divergent controls stay local (grocery's checkbox + swipe-to-mark, pantry's swipe-to-remove/drawer). Define a token (`--accent`, `--success`, …) once in `WidgetShell`'s light + `.dark` blocks and let it cascade — never re-declare a palette token in a widget. The identity and the interactive accent are separate tokens: `--brand` / `--brand-ink` paint only the `BrandMark` tile, while `--accent` / `--accent-ink` paint every interactive use (focus rings, pills, dots, filled buttons, accent text). The light accent is one lightness step darker than the brand (L0.50 vs 0.543) so it clears WCAG AA 4.5:1 as text on accent-tinted fills (the cook flow's active tab and raw-ingredient chips). A control must use `--accent`, never `--brand`, and the light accent must not be lightened back to the brand value. Text on a danger fill uses `--danger-ink`, not a hardcoded value. Editing those values is a visual change; keep it in step with `/DESIGN.md` and `/.impeccable/design.json`, whose token tables mirror them. **Typography is host-matched, not fixed:** `host-style.ts` adopts the host's style tokens (ext-apps `applyHostStyleVariables` / `applyHostFonts`, **value**-imported and resolved at runtime by the import map — ADR-0025) and resolves `--widget-font` — a serif stack for a serif-first host (matched on `userAgent`), the host's `--font-sans` otherwise — which `WidgetShell` consumes; both widgets call `applyHostStyles` on connect and on host-context change. The grouped list draws **one separator per category** (a `border-top` on the sticky `GroupedList` `.aisle`), never a per-row divider. `shared/` is wired into the tsconfigs by **directory glob** (`shared/**/*.ts` in `tsconfig.widgets.json`'s include and both node-side excludes), so a new shared `.ts` is auto-covered — unlike a per-widget `main.ts`, which is per-file. `shared/` has no `main.ts`, so `discoverWidgets` never builds it as a widget.
