# Widgets Feature

## Purpose

The kernel module that serves the interactive widget surface (ADR-0019): it registers the `ui://widget/{name}` resource and serves prebuilt, self-contained HTML for a host to render in a sandboxed iframe. It owns no Paprika entity and reads no config, registers no tool, and exposes `EmptyApi`. A tool opts a result into a widget by declaring `ToolSpec.ui.resourceUri` (the kernel maps it onto `_meta`); this module is the other half — the resource that URI points at.

Canonical home: `docs/architecture.md` ("Widget surface") + [ADR-0019](../../../docs/adr/0019-mcp-app-widget-surface.md). The build pipeline lives in `scripts/build-widgets.ts`; the dev preview in `src/transport/widget-preview.ts`. The **visual design system** — shared with the OAuth consent screen — is the root `/PRODUCT.md` (strategic register), `/DESIGN.md` (Stitch-format visual system), and `/.impeccable/design.json` (machine-readable sidecar).

## Sharp edges

- **`esbuild`, `esbuild-svelte`, `svelte`, and `@modelcontextprotocol/ext-apps` are BUILD-TIME-only devDependencies — nothing on the runtime path may import them.** A widget's HTML is compiled to a self-contained string by `scripts/build-widgets.ts` (the ext-apps browser runtime inlined and all), and the runtime only ever reads that string. A value-import of any of them reaches `dist/` and crashes the prod container (`pnpm install --prod` omits them). `widget-preview.ts` imports `App` **type-only** (erased) for exactly this reason; the `prod-widgets` CI job (`scripts/verify-prod-widgets.mjs`) is the hard gate. esbuild-svelte's default export is non-callable under nodenext (dual CJS/ESM, no `exports` map), so the build loads it via `require` and recovers the factory type.
- **A missing or empty `dist/widgets` DEGRADES (warn + empty map), it does not throw.** The kernel constructs every module regardless of transport, so a hard failure at construction would brick the stdio transport and any `pnpm dev` that has not built widgets. The hard "widgets exist and serve" assertion lives in CI, not at boot. Run `pnpm build:widgets` (or `pnpm dev:widgets` to watch) to populate it locally.
- **One `import.meta.url`-relative path resolves `dist/widgets` from BOTH layouts** (`artifacts.ts`): the built `dist/features/widgets/` and the tsx dev run from `src/features/widgets/` both sit three levels below the repo root, so `../../..` is the root either way and the built widgets always live at `<root>/dist/widgets`. Don't "simplify" to a sibling lookup — it breaks the dev run.
- **Widget browser source is excluded from the two NODE-side tsconfigs but typechecked by `svelte-check`.** A widget's `main.ts` imports its `.svelte` component and uses browser globals, so it is compiled by esbuild and excluded from `tsconfig.json` / `tsconfig.test.json` (`tsc` can't parse `.svelte` and would apply the Node `lib`). Instead `tsconfig.widgets.json` _includes_ exactly those browser entries — `mount-widget.ts`, `*/main.ts`, `**/*.svelte` — with a browser `lib` (DOM) and `types: []`, and `svelte-check` checks them; `pnpm typecheck` chains `typecheck:widgets`, so the pre-push hook and CI cover it. The node-side exclude stays scoped to the browser entries, NOT the whole per-widget subtree: the module and resource files, and the widget feature's tests, stay on `tsc`. (An earlier broad subtree glob silently dropped the test files from typecheck — don't reintroduce it.) A widget with a browser `.ts` beyond `main.ts` must be added to BOTH the node-side excludes AND the `tsconfig.widgets.json` include — otherwise `tsc` tries to compile it (and fails on the `.svelte`/DOM globals) and `svelte-check` never covers it. `svelte-check` runs with `--fail-on-warnings`, matching `oxlint --deny-warnings`: an a11y / unused-CSS / type warning fails the gate, so suppress a deliberate one with a documented `<!-- svelte-ignore … -->`.
- **Widget components use `<script lang="ts">`, but only TYPE-only TypeScript.** Svelte 5 strips type-only syntax (annotations, `import type`, generics, `interface`, `as`/`satisfies`) natively, so the esbuild pipeline needs no preprocessor — `scripts/build-widgets.ts` runs the `esbuild-svelte` plugin (the Svelte 5 compiler) with no `preprocess` option. Non-erasable TS (enums, constructor parameter-properties, decorators) would need a `svelte-preprocess`/`vitePreprocess` step that isn't wired; don't use those features in a widget. The ext-apps `App` type is imported TYPE-only (`import type { App }`) — erased, so ext-apps stays a build-time-only devDependency (the same pattern `transport/widget-preview.ts` uses) while typing every `app.*` bridge call.
- **A list-rendering widget must use a keyed `{#each items (item.uid)}`.** Svelte then updates rows in place, so the scroll position survives a re-render and `animate:flip` can animate a reorder (e.g. a checked item sinking to the bottom of its aisle group). A non-keyed each — or a full `innerHTML` rebuild — recreates the list and resets the scroll. The grocery checklist depends on both.
- **Svelte JS transitions (`slide`/`fly`/`fade`) are NOT CSS transitions, so the `@media (prefers-reduced-motion: reduce)` block does not disable them.** A widget that animates row enter/leave with `transition:` (e.g. the pantry checklist's subtractive remove) must gate the duration in JS — read `matchMedia("(prefers-reduced-motion: reduce)").matches` once and pass `duration: reduced ? 0 : N`. The CSS reduced-motion block still covers the pure-CSS animations (`animate:flip` durations, keyframes), but the imperative transitions slip past it.
- **The `ui://` URI a tool references and the resource registered here must match exactly**, and `{name}` must have a `src/features/widgets/{name}/` source dir — pinned by `test/conformance/widget-ui-references.test.ts`. The resource `list` enumerates the in-memory artifact map loaded at construction, never the directory per request.
- **`.svelte` is linted AND formatted, by two tools that never overlap.** oxlint parses a widget's `<script>` block and applies the repo rules (so widget scripts are covered by `pnpm lint` and the pre-commit hook); oxfmt does **not** recognize `.svelte`, so `prettier` + `prettier-plugin-svelte` format widget markup/styles instead — the `format:svelte` / `format:svelte:check` scripts (chained into `format` / `format:check`) and a `prettier-svelte` pre-commit command, all globbed strictly to `*.svelte`. The split is deliberate: oxfmt owns `.ts`/`.json`/`.md`, prettier owns `.svelte`, and the two never claim the same file. There is **no discoverable prettier config** — the scripts and hook pass `--plugin prettier-plugin-svelte` explicitly — so an editor's Prettier extension can't quietly take over `.ts` and fight oxfmt.
- **`WidgetShell` sizes to content on short lists, capped at the viewport on long ones.** `main` uses `max-height: 100dvh` (NOT `height: 100%`) so a widget with few rows renders compact inside the host iframe rather than leaving a blank gap below. `GroupedList`'s `.scroll` child carries `flex: 1; min-height: 0; overflow-y: auto` — when `main` hits its `max-height`, the scroll area fills the remaining space and activates overflow. `100dvh` uses the dynamic viewport height (adjusting for mobile browser chrome); don't "simplify" this to `100vh` or `100%`.
- **Browser test files in `shared/` are excluded from node tsc but run in vitest.** `host-bridge.test.ts` and `host-style.test.ts` live alongside the source they test; they're typechecked by `tsconfig.widgets.json` (browser lib) via the same `shared/` directory-glob include that covers the source files. Use explicit vitest imports (`import { describe, it, expect, vi } from "vitest"`) — the widget tsconfig has `types: []` so vitest globals are not auto-injected. For DOM-calling code (`host-style.ts`), stub `document` with `vi.stubGlobal` and restore with `vi.unstubAllGlobals()` in `afterEach`. The test harness factory (`test/support/widget-ext-app.ts`) creates duck-typed fake `App` objects and installs `globalThis.ExtApps` spy fakes; import it with a relative path from `shared/`.
- **A widget reads server capabilities from `window[SERVER_CAPS_KEY]` (injected by `widgets-resource.ts` at `resources/read` time), not from the ext-apps host context.** `renderShell` places a `WIDGET_INJECT_SLOT` comment (`<!-- __widget-inject__ -->`) immediately after `<body>`; both `widgets-resource.ts` and `widget-preview.ts` replace that literal string with their `<script>` block — no HTML parsing. The resource handler calls `supportsForm(ctx.server.server)` per-request so each client gets a snapshot of its own negotiated capabilities, serialised as JSON into `window[SERVER_CAPS_KEY]`. The grocery checklist reads it once in `onMount`: when `supportsElicitation` is true it routes "Clear N" directly to `confirmClear()` (letting the server-side `confirmGate` be the sole confirmation) and skips the inline two-tap confirm. The preview shim mirrors this in the `App` constructor from `?elicitation=1`.
- **`SHIMMED_HOST_METHODS` and `SHIMMED_EXTAPPS_HELPERS` in `widget-preview.ts` pin the preview shim surface.** `SHIMMED_HOST_METHODS` pins the `App` instance methods the shim provides against the ext-apps `App` type (so a renamed method fails to compile). `SHIMMED_EXTAPPS_HELPERS` does the same for the four top-level `globalThis.ExtApps` style helpers (`applyHostStyleVariables`, `applyHostFonts`, `applyDocumentTheme`, `getDocumentTheme`) that `host-style.ts` calls; the preview test asserts both lists appear in the served HTML so dropping a helper is caught before it silently breaks the preview or font selection.
- **The dual-mode `receive()` discriminates payloads BY SHAPE.** The meal-week-planner routes the initial result, every nav re-fetch, and the inline recipe read through one `receive()` that tells a `read_meal_plan` week (`weekStart`) from a `read_recipe` slice (`uid` + `ingredients` + `directions`, via `shared/recipe-detail.ts`'s `parseRecipeDetail`). Gotcha: a new structured-output schema carrying that same field cluster would be misread — keep the discriminators distinct. The recipe read is widget-initiated, gated by a non-reactive `pendingRecipeUid` token: any move away (Back, week nav, day select) must null it, or a result that lands after the user left pops the detail pane over the new view. `RecipeDetail.svelte` + `recipe-detail.ts` are shared (two consumers — this widget and recipe-browse); reuse them, don't re-roll the read_recipe parse.
- **`read_meal_plan` re-fetches itself for navigation** (the first widget-bearing read to do so). Prev/next pass the target week's Monday as `startDate` (the today-floor is lifted server-side so past weeks read); `navBusy` locks the arrows mid-fetch. Gotcha: a no-arg `read_meal_plan` (what the assistant calls) anchors its window at today, not Monday, so a mid-week first load is a partial grid — the widget detects this (`weekStart < todayIso`) and realigns to the full week once, kept one-shot by a `primed` flag. Under the `/widget-preview` shim `callServerTool` is a no-op, so navigation, the realign, and recipe taps don't change the view there — hand-roll a data-returning shim to preview those.
- **The shared toolkit is in `shared/`, and `WidgetShell` is the one home of the theme tokens.** The widgets compose `WidgetShell` / `GroupedList` / `ItemRow` / `PillButton` / `Toast` / `StatusScreen` / `BrandMark` / `Spinner` plus the `host-bridge.ts` / `host-style.ts` / `motion.ts` / `group.ts` helpers; only the divergent controls stay local (grocery's checkbox, pantry's swipe/drawer). Define a token (`--accent`, `--success`, …) once in `WidgetShell`'s light + `.dark` blocks and let it cascade — never re-declare a palette token in a widget. Editing those values is a visual change; keep it in step with `/DESIGN.md` and `/.impeccable/design.json`, whose token tables mirror them. **Typography is host-matched, not fixed:** `host-style.ts` adopts the host's style tokens (ext-apps `applyHostStyleVariables` / `applyHostFonts`, reached type-only via the inlined `globalThis.ExtApps`) and resolves `--widget-font` — a serif stack for a serif-first host (matched on `userAgent`), the host's `--font-sans` otherwise — which `WidgetShell` consumes; both widgets call `applyHostStyles` on connect and on host-context change. The grouped list draws **one separator per category** (a `border-top` on the sticky `GroupedList` `.aisle`), never a per-row divider. `shared/` is wired into the tsconfigs by **directory glob** (`shared/**/*.ts` in `tsconfig.widgets.json`'s include and both node-side excludes), so a new shared `.ts` is auto-covered — unlike a per-widget `main.ts`, which is per-file. `shared/` has no `main.ts`, so `discoverWidgets` never builds it as a widget.
