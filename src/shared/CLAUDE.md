# Shared Tool Helpers

## Purpose

The few genuinely cross-cutting helpers the tool layer shares across domains — the ones that belong to no single domain (ADR-0009 §3). Domain-specific helpers (the `*ToMarkdown` formatters, the meal-type spec/resolve) live with their domain under `src/domains/<domain>/`, not here.

**Source is the catalog.** What each file exports, and why, lives in the files' own doc-comments — read them rather than an inventory here. The decisions behind the two non-obvious ones: `resources.ts`'s throw is ADR-0014's recognized form #1; `catalog.ts` is the ADR-0017 machinery.

## Sharp edges

- **`photo-fetch.ts` is the SSRF chokepoint — keep it strict.** It blocks private/loopback/link-local IPs after DNS resolution (not just by hostname), caps the body at `MAX_IMAGE_BYTES`, and is the only sanctioned way to pull a remote image. A photo `source` deliberately has no `file_path` (that would be LFI/SSRF); see `src/domains/recipe/`'s photo tooling and ADR-0004's photo notes.
- **This directory is for cross-domain leaves only.** If a helper is used by exactly one domain, it belongs in that domain. Resist the gravity that pulls unrelated helpers into a shared dir until it becomes a god-bag.
- **`toolResult()`'s two-argument form is the structured-output channel.** `toolResult(text, structuredContent)` carries a `Record<string, unknown>` payload beside the text block (a list wraps its rows as `{ items: [...] }` — `structuredContent` is a record, not a bare array); a tool using it must also declare `outputSchema` on its `ToolSpec` (kernel `CLAUDE.md`). Canonical home: `docs/architecture.md` + ADR-0019.
- **`errorResult()` is the `isError` half of that channel — a schema-bearing tool returns it on every IN-HANDLER non-success branch.** A successful answer (including an empty one) is `toolResult(text, structured)`; an unknown UID / unparseable arg is `errorResult(text)` — otherwise the SDK's `validateToolOutput` eats the friendly message and substitutes a generic schema error (it skips `isError` results). A precondition-GATE failure is NOT this case: the kernel marks gate failures `isError` itself, so a guard returns a plain `toolResult`. `errorResult` returns the precise `ErrorResult` type, not broad `CallToolResult`, so an error branch satisfies the `isError` arm of the kernel's compile-time guard — the `errorResult` / `ErrorResult` doc-comments in `tools.ts` carry the why. Pinned in `tool.e2e.test.ts` (runtime) + `tool.type.test.ts` (compile-time).
- **`imageResult()` returns the human text plus a JPEG image content block (ADR-0019 R2).** `imageResult(text, jpeg)` appends `{ type: "image", data: base64, mimeType: "image/jpeg" }` after the text block so the person sees a rendered image inline — the thumbnail `upload_recipe_photo` just attached, or a `generate_recipe_photo` preview — instead of confirming a photo landed from prose. Callers pass a small normalized JPEG thumbnail (`normalizePhoto` / `makeThumbnail`); the full image stays server-side.
- **`elicit.ts` is the fail-open elicitation gate (ADR-0020 R3) — it never throws into the core.** `confirmGate` (a yes/no before a high-cost act) and `pickOne` (a short disambiguation pick) check the _per-session_ client's advertised `elicitation.form` capability before issuing a request, and catch any SDK throw, so a client that can't be asked yields a typed `unsupported` outcome rather than a raw throw crossing the neverthrow boundary (ADR-0014). The posture is fail-open: a caller treats `unsupported` like proceed (the host's own tool-approval prompt is the backstop), and a declined confirm is a plain `toolResult` ("Cancelled"), never `isError`. The helpers take the minimal `ElicitationServer` slice (`ctx.server.server`), not the whole `McpServer`. Two wrappers in `tools.ts` consume them: `resolveOrPick` runs the `text_many` PICK for the uid-or-text reads, and `confirmOrCancel` runs the destructive-tool CONFIRM (returns the cancel result on decline, `undefined` to proceed). Which destructors gate and why: ADR-0020 + the R3 implementation-design doc.
- **The uid-or-text lookup seam returns `errorResult` (isError) on every non-happy arm — that is what makes the reads `outputSchema`-safe.** `resolveOrPick` / `formatLookupOutcome` (`tools.ts`) resolve a `LookupOutcome` to the entity OR a terminal `errorResult` carrying a `findWith` discovery-verb hint (e.g. `search_recipes`), so a "not found" never travels the success channel a schema-bearing caller validates. Schema-bearing reads call `resolveOrPick` directly — resolving children once and projecting both text and `structuredContent` in one `toolResult(text, structured)` call (no two-closure double-resolve, no text/structured drift); `formatLookupOutcome` is the non-schema helper. `resolveOrPick`'s `result` is the precise `ErrorResult` type so the read handler's error arm satisfies the kernel's compile-time guard. Rationale lives on those functions' doc-comments in `tools.ts`; canonical: `docs/architecture.md` (Structured output channel) + ADR-0019.
- **`mcp-app.ts` mirrors two ext-apps wire constants — mirror, don't import.** `@modelcontextprotocol/ext-apps` is a build-time-only devDependency (a widget's HTML is compiled self-contained and read back as a string), so nothing on the runtime path may import it or `pnpm install --prod` breaks. The MIME type and the legacy `_meta` key are mirrored as local literals and pinned to the installed package by `mcp-app.test.ts`; don't "simplify" by importing them from `@modelcontextprotocol/ext-apps/server`.
