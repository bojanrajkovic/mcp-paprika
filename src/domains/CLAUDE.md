# Domain Modules

## Purpose

One directory per cohesive domain — the unit the kernel constructs, isolates, and sync-drives. A domain owns one or more Paprika entities, declares its dependencies, and exposes a public contract (`api.ts`) that sibling domains reach along a declared `dependsOn` edge.

## Layout (per domain)

- `module.ts` — the domain's kernel registration (`defineModule(…).state(…).build(…)`), augmenting `DomainRegistry` with its contract type. The builder shape and the pure-`*State` / `ctx.writes` split live in `../kernel/CLAUDE.md` and [ADR-0012](../../docs/adr/0012-pure-state-and-writes-seam.md), not here.
- `api.ts` — the read contract siblings depend on (kept narrow; this is the only surface another domain sees).
- `ids.ts` — the domain's branded-UID leaf: every brand its entities own, sub-entities included (recipe's carries `CategoryUid` + `PhotoUid`). It imports nothing but zod, and one leaf owns each brand string — both conformance-gated (`test/conformance/uid-leafs.test.ts`, [ADR-0016](../../docs/adr/0016-per-domain-uid-leafs.md)). An FK consumer imports the owning domain's leaf directly.
- The defining entity's `types.ts` / `store.ts` at the domain root; each **additional** owned entity in an `<entity>/` subdir (e.g. `recipe/category/`, `recipe/photo/`, `grocery/grocery-item/`, `menu/menu-item/`). `types.ts` also holds the entity's `DiskCacheDescriptor` (the cache's `subdir`/`parse`/`getKey`); a dedicated `disk.ts` appears only for a cache that carries behavior beyond a descriptor (`recipe/disk.ts`'s `RecipeDiskCache`).
- `tools/`, `resources/` — co-located, tests beside them; tool readiness gates live in `tools/guards.ts`. The reconcile is a flat `sync.ts` at the domain root, promoted to a `syncs/` directory only when a domain has more than one sync or a co-located sync test (`recipe/`, `grocery/`, `menu/`). Domain-specific markdown formatters live here too (e.g. `recipe-markdown.ts`, `grocery-helpers.ts`); genuinely cross-cutting helpers live in `src/shared/`.

The domain graph (who `dependsOn` whom) and the ownership rule are in [ADR-0009 §3](../../docs/adr/0009-domain-isolated-tool-modules-kernel.md), drawn there as a diagram.

## File granularity

The rule across the per-domain concerns: **co-locate at the lightest granularity that keeps a thing findable; spend a separate file or directory only when it is substantial, multiple, or separately tested.** The discriminator is demonstrated need — a real second instance, a co-located test, behavior beyond a literal — not anticipated need.

- **A trivial disk-cache descriptor lives in the entity's `types.ts`**, beside the schema its `parse` calls; a dedicated `disk.ts` is reserved for a cache that carries behavior (`recipe/disk.ts`'s `RecipeDiskCache`). The auth caches aren't Paprika entities — their descriptor + subclass sit in `../auth/disk.ts`.
- **A single, untested reconcile is a flat `sync.ts` at the domain root**; `syncs/` is for a domain with more than one sync or a co-located sync test (`recipe/`, `grocery/`, `menu/`). A second sync or a `sync.test.ts` promotes a domain to the directory.
- **A tool readiness gate lives in `tools/guards.ts`**, passed as a kernel precondition via `defineTool(spec, [xStartGuard], ctx => …)` (ADR-0015). Single-state gates take a `{ readonly state: XState }` slice; cross-domain gates take a fuller `DomainCtx`. A tool that needs an extra readiness leg beyond its primary gate adds a second named guard to the array. The auto-create api paths (`ensureAisle` / `ensureMealType`) guard the same precondition inline because they sit mid-write-flow, not in a tool. A high-cost destructor's CONFIRM gate (ADR-0020) is the opposite kind — async and argument-dependent (it names the entity, and counts a bulk act), so it lives IN the handler via `confirmOrCancel(ctx.server.server, …)` after the entity resolves and the refusal checks pass, never in the precondition array.

## Sharp edges

- **Disk stays flat; the source layout is namespaced but the cache dir is not.** A child entity nested at `src/domains/recipe/category/` still writes to `<cacheDir>/categories` — its `DiskCacheDescriptor.subdir` is the flat on-disk name, reuse-in-place, so the reshape needed no on-disk migration. Don't "align" the subdir to the source path; that would orphan every deployed cache. See ADR-0009 §3.
- **A sibling's STATE-BEARING behavior is reached only via `ctx.deps.<id>.<contract>`; its PURE LEAVES may be imported directly.** The line is whether the thing touches the sibling's domain state. State-bearing behavior — anything that reads/resolves against a sibling's store or catalog, or writes it — rides the providing domain's `api`, never its store, `state`, or internal stateful helper: a meal row is `ctx.deps.meal.toRows(meals)`, a pantry row is `ctx.deps.pantry.toRows(items)`, an aisle display name is `ctx.deps.aisle.displayName(item)`, a meal-type resolve-or-create is `ctx.deps["meal-type"].resolveOrCreate(spec)`. The providing domain implements these in its `.build` — which receives its OWN declared deps (see `../kernel/CLAUDE.md`), so an `api` method can resolve across one more boundary internally (a pantry row resolving the aisle catalog through pantry's aisle dep, a meal row resolving the type name through meal's meal-type dep) without the consumer touching that further catalog. Pure leaves carry no domain state to encapsulate, so a sibling imports them directly: another domain's branded ids, its schemas and their inferred types (`recipeRowSchema`, `mealTypeSpecSchema`, `MealTypeSpec`, `addPantryItemsOutputSchema`), and its STATELESS formatters (`recipeMetadataLines`, `formatMealTypeResolveError` — pure `(value) => string` projections). Adding a state-bearing edge means adding it to the `dependsOn` tuple (the single source of truth for what `deps` carries) AND importing the dependency's brand along that same edge.
- **A domain that owns a parent + its children fires its own `resourceListChanged()`.** Grocery owns lists + items, menu owns menus + items; a child-item change invalidates the parent resource, so the commit chokepoint (assembled in `module.ts`'s `.build`, reached by the domain's own tools via `ctx.writes`) emits it. There is no central change-type table.
- **`hasSynced` has two layers — don't blanket-expose it on a contract.** Every store carries `hasSynced` (the `EntityStore` base property) for INTERNAL cold-start self-gating, reached via `ctx.state.<store>.hasSynced` (grocery's `groceryStartGuard`, aisle's list tool). A domain's `api.ts` exposes `hasSynced()` to siblings (via `extends HasSynced` from the kernel) ONLY when a SIBLING gates a cross-domain call on it — recipe / meal / menu / meal-type / pantry have such a consumer; grocery (no sibling reads it) and aisle (consumers resolve against the last-good catalog, ADR-0010) self-gate and expose nothing. Adding it to a contract with no sibling consumer is speculative surface — the same "scoped to live cross-domain call sites" discipline every `api.ts` header states.
- **Export only the real contract; keep private sub-shapes file-local.** `module.ts` exports the intra-domain ctx contracts its own co-located tools/syncs import (`<Domain>State`, `<Domain>Writes`) but NOT the private helper shapes that compose them — the `*EntitySlice` store+cache pairs are `interface`s with no `export`, used only to build `*State` in the same file. A schema's inferred type lives beside its schema, not in `api.ts`: the shared `MealTypeSpec` (`z.infer<typeof mealTypeSpecSchema>`) sits in `meal-type-helpers.ts` next to the schema, so the sites that annotate a spec value name `MealTypeSpec` instead of re-spelling `z.infer<typeof …>` — the `resolveSpec`/`resolveOrCreateMealType` params (the latter still the meal-type-internal impl behind the `ctx.deps["meal-type"].resolveOrCreate(spec)` contract method consumers call) and `log_cooked_meal`'s default. (Tools that only pass the schema's parsed `args.type` straight through don't annotate it, so they keep importing just the schema.)
