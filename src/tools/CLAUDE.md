# MCP Tool Definitions

Last verified: 2026-05-30

> Pantry write tools (`add_pantry_items`, `update_pantry_item`) normalize any user-supplied `expirationDate` through `normalizePaprikaDate()` (`paprika/dates.ts`) before persisting. Accepts ISO 8601, `yyyy-MM-dd`, `yyyy/MM/dd`, or the already-Paprika `yyyy-MM-dd HH:mm:ss`. Unparseable input returns a `textResult` error to the LLM rather than writing garbage. `add_pantry_items` stamps `purchaseDate` via `paprikaDateToday()` (today at midnight, Paprika wire format) and generates UIDs as **uppercase** UUID v4 to match what Paprika.app emits.

Purpose: Defines MCP tools that AI assistants can invoke. Each tool file exports a `register*` function that takes `(server: McpServer, ctx: ServerContext)` and calls `server.registerTool()`. Tools with external dependencies (e.g., vector store) accept additional parameters after `ctx`.

## Registration Pattern

Every tool file exports a single registration function. All tool logic accesses data through `ctx.store` (the `RecipeStore` on `ServerContext`), never by importing `paprika/` or `cache/` directly at runtime.

```typescript
import { coldStartGuard, textResult } from "./helpers.js";

export function registerMyTool(server: McpServer, ctx: ServerContext): void {
  server.registerTool(
    "tool_name",
    {
      description: "...",
      inputSchema: {
        /* zod */
      },
    },
    async (args) => {
      return coldStartGuard(ctx).match(
        async () => {
          /* store is ready */ return textResult("result");
        },
        (guard) => guard,
      );
    },
  );
}
```

**Variant: external dependencies.** Tools that require services beyond `ServerContext` accept additional constructor-injected parameters. Example: `registerDiscoverTool(server, ctx, vectorStore: VectorStore)` receives the vector store instance from `index.ts`.

## Logger pattern

Each `register*Tool(server, ctx)` creates its own component-scoped child logger at the top of the function body:

```typescript
const log = ctx.log.child({ component: "<mcp-tool-name>" });
```

Component names match the MCP tool name in snake_case (e.g., `add_pantry_items`, `create_recipe`). The child is captured in the handler closures and lives for the session lifetime.

Catch sites use pino's structured method form: `log.error({ err, ...identifyingFields }, "operation failed")`. The identifying fields are the request-scope keys available before the failure (e.g., `uid`, `ingredient`, `name`) — not the full args object. The user-facing `textResult` keeps a human-readable message; the structured record is separate.

Error-level records fan out to connected MCP clients automatically via the multistream (error ≥ default `notifyLevel: "warn"`).

## Shared Helpers

### `helpers.ts`

Utilities imported by recipe tool handlers from `./helpers.js`.

- **`textResult(text)`** -- Wraps a string in the MCP `CallToolResult` envelope.
- **`coldStartGuard(ctx)`** -- Returns `Ok<void>` when store is synced, `Err<CallToolResult>` when empty. Always use `.match()` to handle both branches.
- **`uidOrTextLookupSchema({ uidSchema, textKey, entityLabel, textExample?, textDescribe? })`** -- Builds the shared "look up by exact UID OR by a fuzzy text field" input schema for `read_recipe`, `read_grocery_list`, and `get_pantry_item`. A `z.union` of two `.strict()` objects dispatched by property presence — the same shape and rationale as `mealTypeSpecSchema` (meal-helpers). The UID member is branded (`uidSchema`, e.g. `RecipeUidSchema`) so `args.lookup.uid` is already brand-typed after parse (no cast at the store lookup), and `z.string().min(1).brand(...)` keeps the non-empty guard. `textKey` stays per-entity (`title` / `ingredient` / `name`); the text-member describe defaults to a template from `entityLabel` + `textKey` + `textExample`, or pass `textDescribe` to override it verbatim (e.g. `get_pantry_item` uses "Ingredient name fuzzy match", which reads better than the templated "Pantry item ingredient fuzzy match").
- **`resolveLookup(query, { get, findByText })`** -- Resolver mirroring `resolveMealTypeSpec`: classifies a normalized `LookupQuery` (`{uid}` or `{text}`, which the caller derives via its own `"uid" in lookup` check) into a `LookupOutcome` discriminated union (`uid_hit` / `uid_miss` / `text_none` / `text_one` / `text_many`). Key-agnostic — the caller extracts its own text key before calling. Never formats user-facing text.
- **`formatLookupOutcome(outcome, { entityNoun, renderOne, disambiguationLine })`** -- Renders a `LookupOutcome` to a `CallToolResult` with wording consistent across the three lookup tools (`No {noun} found with UID …` / `No {noun}s found matching …` / `Multiple {noun}s match …`). `renderOne` supplies the single-entity markdown; `disambiguationLine` supplies one multi-match bullet (kept per-entity so each tool's existing line format is preserved). Plural is `entityNoun + "s"`.
- **`recipeToMarkdown(recipe, categoryNames, lastCookedAt?)`** -- Renders a full recipe as markdown. Resolve categories via `ctx.store.resolveCategories()` before calling. When `lastCookedAt` is provided (non-null string), appends a `**Last Cooked:** {date-only}` line. Omits empty optional fields.
- **`commitRecipe(ctx, saved)`** -- Persists a saved recipe to cache and store, triggers cloud sync. Order: `ctx.store.markPendingUpsert(saved.uid)` or `markPendingDelete(saved.uid)` based on `saved.inTrash` (sync, FIRST) → `cache.recipes.put` (async) → `cache.flush` (async) → `store.set` (sync) → `ctx.notifier.resourceListChanged()` (sync) → `notifySync` (async). The pending-write mark is set BEFORE any cache I/O so an in-flight sync cycle that observes the cache mid-commit (between awaits) still sees the pending-write flag and skips reconciling our UID. See `cache/CLAUDE.md` Pending-writes section. Called by all write tools after `ctx.client.saveRecipe()`. **Note:** even the soft-delete (`inTrash: true`) path still `put`s and `set`s the recipe — a trashed recipe stays in the store (hidden from listings via `getAll`/`search`, but returned by `get(uid)`). `empty_trash` does NOT rely on this, though: it fetches authoritative `inTrash` state from Paprika so it also catches recipes trashed app-side that the local store hasn't synced yet.
- **`commitRecipeHardDelete(ctx, saved)`** -- Hard-delete (empty-trash) commit: the recipe is gone server-side, so this REMOVES it locally (vs `commitRecipe`, which put+sets even for a trashed recipe). Order: `markPendingDelete(uid)` (sync, FIRST) → `cache.recipes.remove` (async) → `cache.flush` (async) → `store.delete` (sync) → `resourceListChanged()` (sync) → `notifySync` (async). Mark-first ordering and the `clearPending` on cache-failure mirror `commitRecipe`. Called only by `empty_trash` after `ctx.client.saveRecipe()` of the `{inTrash, deleted}` tombstone.
- **`resolveCategoryNames(all, names)`** -- Resolves human-readable category display names to UIDs. Case-insensitive linear scan. Returns `{ uids, unknown }` for warnings.

> **Branded UID input schemas.** Tool input fields that carry an entity UID use the branded `XxxUidSchema` (from `paprika/types.ts`) directly — `uid: RecipeUidSchema.describe(...)`, `uids: z.array(GroceryItemUidSchema)`, `recipe_uid: RecipeUidSchema.optional()`. The brand is type-only at runtime (the wire still accepts strings), so `args.uid` is already brand-typed after Zod parse and flows into `ctx.store.get(...)` with no `XxxUidSchema.parse(args.uid)` / `as RecipeUid` cast at the lookup site. The remaining `XxxUidSchema.parse(...)` calls in tool code are for **generated** UIDs (`crypto.randomUUID()`) or **server-derived** strings (catalog `aisleUid`, vector-index `result.uid`), not tool inputs.

### `aisle-helpers.ts`

Utilities for aisle resolution imported by pantry write tools from `./aisle-helpers.js`.

- **`aisleStartGuard(ctx)`** — Returns `Ok<void>` when `ctx.aisleStore.hasSynced`, `Err<CallToolResult>` otherwise. Used by `list_aisles`.
- **`commitAisle(ctx, aisle)`** — Upsert-only commit: `markPendingUpsert(uid)` (sync, FIRST) → `cache.aisles.put` (async) → `cache.flush` (async) → `aisleStore.set` (sync) → `notifySync` (async). Wraps cache I/O in try/catch that calls `clearPending(uid)` on failure. No delete branch — aisles are never deleted from the server-side via this server.
- **`ensureAisle(ctx, name)`** — Resolves an aisle display name to `{ aisle: string, aisleUid: string }`. Empty string → `{aisle: "", aisleUid: ""}` without I/O. Found in store → `{aisle: match.name, aisleUid: match.uid}` without I/O. Not found → auto-creates via `client.saveAisle()` using an uppercase UUID v4 UID (matching Paprika.app's wire format for user-created aisles; built-in default aisles use 64-char uppercase hex). Called by `add_pantry_items` and `update_pantry_item` write tools.

### `pantry-helpers.ts`

Utilities imported by pantry tool handlers from `./pantry-helpers.js`.

- **`pantryStartGuard(ctx)`** -- Returns `Ok<void>` when pantry is synced, `Err<CallToolResult>` when not yet synced. Always use `.match()` to handle both branches.
- **`pantryItemToMarkdown(item)`** -- Renders a pantry item as markdown with ingredient, UID, and in-stock status (always rendered) plus quantity, aisle, expiration date, purchase date, and notes when present (omits empty strings and `null` optional fields).
- **`commitPantryItem(ctx, saved)`** -- Persists a saved pantry item to the local cache and store, then triggers cloud sync. Branches on `saved.deleted`: the upsert branch calls `pantryStore.markPendingUpsert(saved.uid)` (sync, FIRST) → `cache.pantry.put` (async) → `cache.flush` (async) → `pantryStore.set` (sync) → `notifySync` (async); the delete branch calls `pantryStore.markPendingDelete(saved.uid)` (sync, FIRST) → `cache.pantry.remove` (async) → `cache.flush` (async) → `pantryStore.delete` (sync) → `notifySync` (async). The pending-write mark is set BEFORE any cache I/O so an in-flight sync cycle that observes the cache mid-commit still sees the pending-write flag and skips reconciling our UID (see `cache/CLAUDE.md` Pending-writes section). Called by all pantry write tools after `ctx.client.savePantryItems()`. Do NOT call `ctx.client.notifySync()` separately in the tool handler — `commitPantryItem` already calls it. No `resourceListChanged()` is emitted — pantry items have no resource surface.
- **`commitPantryItemsBatch(ctx, items)`** -- Batch variant of `commitPantryItem`. Commits N items with a single `cache.flush()` and a single `notifySync()`. Marks all pending writes before any cache I/O; on cache failure, clears ALL marked UIDs before re-throwing so no UID is left shielded until TTL. No `resourceListChanged()` — pantry has no MCP resource surface. Used by `add_pantry_items` and `move_to_pantry`.

### `grocery-item.ts`

Exports `registerAddGroceryItemsTool`, `registerUpdateGroceryItemTool`, and `registerDeleteGroceryItemTool`. Key design notes:

- **Batch-add semantics:** `add_grocery_items` accepts `listUid` + `items` array (1..N). Aisle resolution and ingredient catalog updates happen in the validation phase (all-or-nothing) before the single `ctx.client.saveGroceryItems(builtItems)` batch POST. The returned array is committed via `commitGroceryItemsBatch` (one flush, one resourceListChanged, one notifySync).
- **Ingredient catalog update:** When an explicit `aisle` is provided, the handler calls `ctx.client.saveGroceryIngredient(...)` to update (or create) the catalog entry. **The local `GroceryIngredientStore` is NOT updated** — it has no `set` method (replace-all only). The catalog reflects the new aisle on next sync cycle.
- **Aisle fallback to Miscellaneous:** When no aisle is specified AND the ingredient has no catalog memory (or the remembered aisle no longer resolves), the item is placed in the built-in **Miscellaneous** aisle (resolved by name from `aisleStore`), matching Paprika.app, which never leaves an item aisle-less. Falls back to `""` only when the catalog has no Miscellaneous aisle (user-deleted or non-English) — never auto-creates it, since it's a Paprika built-in. No ingredient-catalog entry is written for a Miscellaneous-default placement: Miscellaneous is a default, not learned aisle memory, so writing it would contradict the sync layer's drop of no-aisle ingredients.
- **`name` denormalization:** The `name` field stores `"${quantity} ${ingredient}"` when quantity is non-empty, just `"${ingredient}"` when empty. Recalculated on update.
- **No duplicate guard:** Unlike `add_pantry_items`, there is no code-level duplicate-ingredient check. The tool description instructs the LLM to call `read_grocery_list` before adding.

### `grocery-helpers.ts`

Utilities imported by grocery list tool handlers from `./grocery-helpers.js`.

- **`groceryStartGuard(ctx)`** -- Returns `Ok<void>` when both `ctx.groceryListStore.hasSynced` and `ctx.groceryItemStore.hasSynced` are true, `Err<CallToolResult>` otherwise. Both stores must be synced because `read_grocery_list` inlines items. Always use `.match()` to handle both branches.
- **`commitGroceryList(ctx, saved)`** -- Persists a saved grocery list to the local cache and store, then triggers cloud sync. Branches on `saved.deleted`: the upsert branch calls `groceryListStore.markPendingUpsert(saved.uid)` (sync, FIRST) → `cache.groceryLists.put` (async) → `cache.flush` (async) → `groceryListStore.set` (sync) → `ctx.notifier.resourceListChanged()` (sync) → `notifySync` (async); the delete branch calls `groceryListStore.markPendingDelete(uid)` (sync, FIRST) → `cache.groceryLists.remove` (async) → `cache.flush` (async) → `groceryListStore.delete` (sync) → `ctx.notifier.resourceListChanged()` (sync) → `notifySync` (async). Unlike `commitPantryItem`, both branches call `ctx.notifier.resourceListChanged()` after the store mutation — grocery lists have an MCP resource surface (pantry items do not). The pending-write mark is set BEFORE any cache I/O; cache I/O is wrapped in try/catch that calls `clearPending(uid)` on failure. Called by all grocery list write tools after `ctx.client.saveGroceryList()`.
- **`commitGroceryItem(ctx, saved)`** -- Same pattern as `commitGroceryList` but operates on `groceryItemStore` and `cache.groceryItems`. Also calls `ctx.notifier.resourceListChanged()` after the store mutation because items are inlined in the list resource surface. Used by single-item tools (`update_grocery_item`, `delete_grocery_item`).
- **`commitGroceryItemsBatch(ctx, items)`** -- Batch variant of `commitGroceryItem`. Commits N items with a single `cache.flush()`, a single `ctx.notifier.resourceListChanged()`, and a single `notifySync()`. Marks all pending writes before any cache I/O; on cache failure, clears ALL marked UIDs before re-throwing. Used by `add_grocery_items`, `clear_purchased`, `clear_all`, and `move_to_pantry`.
- **`groceryListToMarkdown(list, items)`** -- Renders a grocery list as markdown. Outputs the list name as H1, UID, item count, then a markdown table of items (ingredient, quantity, aisle, purchased status). Empty string fields render as `—`.
- **`groceryItemToMarkdown(item)`** -- Renders a single grocery item as markdown. Outputs ingredient as H1, UID, list UID, then conditionally quantity, aisle, purchased status, and instruction/notes when non-empty.

### `menu-helpers.ts`

Shared plumbing for the menu surface, imported from `./menu-helpers.js`. Cloned from `grocery-helpers.ts` (the parent/child Content+Data pair), NOT from `meal-helpers.ts` — menus have an MCP resource surface, so the commit helpers DO emit `resourceListChanged()` (the meal helpers do not).

- **`menuStartGuard(ctx)`** -- Returns `Ok<void>` when `ctx.menuStore.hasSynced`, `ctx.menuItemStore.hasSynced`, AND `ctx.mealTypeStore.hasSynced` are all true, `Err<CallToolResult>` otherwise. The menu + menu-item stores back a menu and its inlined items; the meal-type store is required because `read_menu`, the menu write tools, and the menu resource render each item's meal-type name and sort within a day by the type's order — and meal-type sync is best-effort (can lag/fail independently of menu sync), so without this check a cold catalog renders items with opaque `typeUid`s sorted as unknown. Mirrors `mealStartGuard` (which likewise gates on `mealTypeStore`), not `groceryStartGuard`. Always use `.match()` to handle both branches.
- **`menuToMarkdown(menu, items, mealTypes, opts?)`** -- Pure renderer for a menu and its items. Iterates the menu's full `days` span (Day 1..menu.days); a day with no items renders `_(no meals planned)_`. Within a day, items sort by their meal-type's `orderFlag` (an unknown `typeUid` sorts last), then by item `orderFlag`. Header: menu name (H1), UID, `Days: N`, and `Notes:` when non-empty. Each item line shows the resolved meal-type name and the recipe display name (`item.name`). When `opts.includeItemUids` is set, appends `` · item `<uid>` · recipe `<recipeUid>` `` (recipe clause omitted when `recipeUid` is null). Pure like `mealToMarkdown` — takes the `mealTypes` catalog array for `typeUid`→name/order resolution; both callers pass `ctx.mealTypeStore.getAll()`. `read_menu` passes `includeItemUids: true`; the `paprika://menu/{uid}` resource passes `false` (clean recipe-name lines, matching `groceryListToMarkdown`'s no-child-UID convention).
- **`commitMenu(ctx, saved)`** -- Persists a saved menu to cache and store, then triggers cloud sync. Clone of `commitGroceryList`: branches on `saved.deleted` (markPending\* → put/remove → flush → set/delete → resourceListChanged → notifySync), wraps cache I/O in try/catch that calls `clearPending` on failure. Both branches call `ctx.notifier.resourceListChanged()` because menus have an MCP resource surface.
- **`commitMenuItem(ctx, saved)`** -- Same pattern as `commitMenu` but operates on `menuItemStore` and `cache.menuItems`. Calls `resourceListChanged()` because menuitems are inlined in the menu resource. Used by single-item write tools.
- **`commitMenuItemsBatch(ctx, items)`** -- Batch variant of `commitMenuItem`. Commits N menuitems with a single `cache.flush()`, a single `resourceListChanged()`, and a single `notifySync()`. Marks all pending writes before any cache I/O; on cache failure (via `Promise.allSettled`), clears ALL marked UIDs before re-throwing.

### `meal-helpers.ts`

Utilities imported by meal tool handlers from `./meal-helpers.js`.

- **`mealTypeSpecSchema`** -- Exported Zod `z.union` of three `.strict()` objects for meal type resolution: `{name}` (trims whitespace via `.transform()`), `{uid}`, and `{builtin}`. Property-presence dispatch — callers pass exactly one variant. Used by both `meal-history.ts` and `meal-writes.ts`.
- **`resolveMealTypeSpec(ctx, spec)`** -- Shared type-DU resolver used by `meal-history.ts` (read) and `meal-writes.ts` (write). Resolves a `mealTypeSpecSchema` variant against `mealTypeStore` and returns a `MealTypeResolveResult` discriminated union: `{ok: true, resolved: MealType}` on a hit, or one of three error reasons (`unknown_uid` / `unknown_name` with `knownNames` for hinting / `unknown_builtin`). Never formats user-facing text — each caller maps the reason to its own message style (per-index-prefixed for `add_meals`, single-filter for `update_meal` / `list_meal_history`) and derives its own projection from the resolved `MealType` (the read side reads `originalType` to surface legacy null-`typeUid` meals; the write side sends `originalType ?? 0` as the vestigial wire integer).
- **`mealStartGuard(ctx)`** -- Returns `Ok<void>` when BOTH `ctx.mealStore.hasSynced` AND `ctx.mealTypeStore.hasSynced` are true, `Err<CallToolResult>` otherwise. The mealtype check is required because `resolveMealTypeSpec` reads from `mealTypeStore` — without it, cold-cache lookups surface as misleading "Unknown meal type" errors instead of a clear "still syncing" message. Always use `.match()` to handle both branches.
- **`mealTypeStartGuard(ctx)`** -- Returns `Ok<void>` when `ctx.mealTypeStore.hasSynced`, `Err<CallToolResult>` otherwise. Narrower than `mealStartGuard` (no `mealStore` check) — used by the read-only `list_meal_types` tool, which only touches the meal-type catalog. Mirrors `aisleStartGuard`. Always use `.match()` to handle both branches.
- **`makeMealOrderFlagAssigner(ctx)`** -- Builds a stateful per-DATE `order_flag` assigner `(date) => number` for a batch of new meals. `order_flag` sequences per calendar date across ALL meal types — the wire capture shows two same-date meals of different types posting as 0 and 1, while two same-type meals on different dates both post as 0 (`docs/wire-captures/meals.har.json`). Seeds each date from `MealStore.getMaxOrderFlagOn(date)` and increments a per-date counter across the batch (the built meals aren't in the store yet, so a per-batch counter is required to avoid same-date collisions). Shared by `add_meals` (Stage 2) and `add_menu_to_planner` so the per-date sequencing lives in one tested place. `update_meal` does NOT use it — it moves a single meal and calls `getMaxOrderFlagOn(destDate) + 1` directly, only when the date changes.
- **`commitMeal(ctx, saved)`** -- Persists a saved meal to the local cache and store, then triggers cloud sync. Same pending-marks-then-cache-then-store-then-notifySync sequence as `commitPantryItem`: the upsert branch calls `mealStore.markPendingUpsert(saved.uid)` (sync, FIRST) → `cache.meals.put` (async) → `cache.flush` (async) → `mealStore.set` (sync) → `notifySync` (async); the delete branch calls `mealStore.markPendingDelete(saved.uid)` (sync, FIRST) → `cache.meals.remove` (async) → `cache.flush` (async) → `mealStore.delete` (sync) → `notifySync` (async). No `ctx.notifier.resourceListChanged()` is emitted — meals have no MCP resource surface.
- **`commitMealsBatch(ctx, items)`** -- Batch variant of `commitMeal`. Commits N meals with a single `cache.flush()` and a single `notifySync()`. Marks all pending writes before any cache I/O; on cache failure, clears ALL marked UIDs before re-throwing. No `resourceListChanged()` — meals have no MCP resource surface. Used by `add_meals`.
- **`mealToMarkdown(meal, typeName, recipeName)`** -- Pure renderer for a single meal. Takes pre-resolved display names from the caller (caller is responsible for looking up `typeName` from `mealTypeStore` and `recipeName` from recipe store).
- **`renderMealCard(ctx, meal)`** -- ctx-aware wrapper over `mealToMarkdown`: resolves `typeName` from `mealTypeStore` (with the `Type N` fallback for unknown/legacy types) and `recipeName` from the recipe store, then renders. Collapses the four identical lookup-then-render blocks the `add_meals` / `update_meal` response paths used to repeat. Builds the (tiny) type-name map per call so the signature stays `(ctx, meal)`. The pure `mealToMarkdown` remains for callers that already hold resolved names.

### `meal-writes.ts`

Exports `registerAddMealsTool`, `registerUpdateMealTool`, and `registerDeleteMealTool`. All three meal write tools live in one file, mirroring `grocery-item.ts`'s multi-tool pattern. Also exports `addMealsInputSchema` and `updateMealInputSchema` for direct Zod-validation tests.

`registerAddMealsTool` and `registerUpdateMealTool` resolve the `mealTypeSpecSchema` union variant via the shared `resolveMealTypeSpec` helper (exported from `meal-helpers.ts`, also used by `list_meal_history`). It returns a `MealTypeResolveResult` discriminated union: `{ok: true, resolved: MealType}` on hit, or one of three error variants (`unknown_uid` / `unknown_name` with `knownNames` for hinting / `unknown_builtin`) that callers map to user-facing messages. Built-in meal types carry `originalType: 0..3` (Breakfast/Lunch/Dinner/Snacks); user-created custom types carry `originalType: null`. When `typeUid` is set, the wire `type` integer is vestigial — Paprika.app dispatches display off `type_uid`, and the server preserves whatever integer we POST. Custom-type writes therefore send `type: 0` (the `?? 0` fallback) so the value round-trips through `mealsEqual` cleanly. Verified via direct API experiment + UI eyeball, 2026-05-29.

**Schema shape (recipe XOR name).** Both `mealItemInputSchema` (inside `add_meals`) and the `update` payload in `update_meal` are `z.union` of `.strict()` objects rather than flat objects with `.refine()`. This is a deliberate UX decision: Paprika.app's UI dispatches the displayed meal name off `recipe_uid` for linked meals and would never render a stored custom `name` on a recipe-linked meal, so a stored custom name there is dead data. Rejecting `{recipe_uid, name}` structurally (matches no variant) surfaces the constraint at the Zod boundary instead of letting callers ship invisible data. Same rationale drives the runtime guard in `update_meal` that rejects the `name`-only variant on already-recipe-linked meals.

**Date handling.** Both `add_meals` and `update_meal` normalize the `date` argument via `parseInputMealDate` (`utils/dates.ts`). For offset-bearing ISO inputs the user's local calendar day is preserved — `2026-06-15T22:00:00-08:00` is stored as `2026-06-15 00:00:00`, not UTC-shifted to June 16 — because the meal planner is day-granular and the wire string is a calendar-day label rather than a UTC instant. `list_meal_history` still uses `parseInputDate` + `toWireDateFormat` for its since/until comparisons, which remain UTC-anchored.

**order_flag is per-DATE, not per-(date, type).** `add_meals` Stage 2 and `update_meal`'s date-move reassignment both treat `order_flag` as a single sequence across all meal types on a calendar day — the wire capture is decisive (two same-date meals of different types post as 0 and 1; two same-type meals on different dates both post as 0; `docs/wire-captures/meals.har.json`). `add_meals` uses `makeMealOrderFlagAssigner`; `update_meal` re-sequences (`getMaxOrderFlagOn(destDate) + 1`) ONLY when the `date` changes — a type change that keeps the date preserves the flag (keep-the-position).

### `meal-add-menu.ts`

Exports `registerAddMenuToPlannerTool` plus `addMenuToPlannerInputSchema` for direct Zod-validation tests. The `add_menu_to_planner` cross-entity tool instantiates a saved menu's items as dated meal-planner entries. It lives in the meal family (produces meals), mirroring how `move_to_pantry` lives with grocery. Notes on the non-obvious behavior:

- **Three-guard composition.** `coldStartGuard(ctx)` (recipe store — names re-resolve) `.andThen(menuStartGuard(ctx))` (menu + menuitem + mealType), then an explicit `if (!ctx.mealStore.hasSynced)` check inside the match — it POSTs meals. Mirrors `move_to_pantry`'s grocery-guard + explicit pantry check.
- **Projection, not a link.** Each `MenuItem` materializes into a `Meal` dated `start_date + (day − 1)` days (via `parseInputMealDay` + `toMealWireDate`, clamping the `day: 0` the schema permits). The posted meals carry NO `menu_uid` — the planner copy is decoupled. Consequently the tool is intentionally NON-idempotent (re-running adds another copy) and does no de-dup against existing planner meals.
- **Strict recipe re-resolution.** Display names re-resolve from `ctx.store` (not the menu item's denormalized `name`); ANY recipe-linked item whose recipe is unknown rejects the WHOLE batch with a per-item enumeration — exactly like `add_meals` / `add_menu_items`. Freeform items (`recipeUid: null`) always materialize from their stored `name`. A missing/custom `typeUid` is fine: `type` falls back to the vestigial `0` and the `typeUid` is preserved.
- **Menu-layout ordering → per-DATE order_flag.** Items are sorted into the menu's intended layout — `day`, then meal-type `orderFlag`, then the item's own `orderFlag` — BEFORE materialization, because `getByMenuUid` returns arbitrary store-insertion order. `order_flag` is then assigned in that order via `makeMealOrderFlagAssigner` (shared with `add_meals`), so same-date meals sequence by meal type (matching the wire capture: a Breakfast/Lunch pair on one date posts as 0/1 in type order) and the persisted flags are deterministic. The capture's two-day menu lands its day-1 and day-3 Dinners on different dates, each `order_flag 0`.
- **Compact response.** Day-grouped (`## <date> (Day N)` with `- **<type>:** <name>` bullets), header `Added N meal(s) … (Day 1 = <date>)`. The renderer consumes the already-layout-sorted materialized list (so the displayed sequence matches the persisted `order_flag` order) and rebuilds no meal-type map. No per-meal UIDs — scales to a 21-meal week; an agent needing a UID afterward calls `list_meal_history`.

### `menu-write.ts`

Exports `registerCreateMenuTool`, `registerUpdateMenuTool`, and `registerDeleteMenuTool`. All three menu write tools live in one file, mirroring `grocery-list.ts`'s create/rename/delete trio. Each resolves through `menuStartGuard` and commits via the `menu-helpers.ts` helpers (`commitMenu` for the menu, `commitMenuItemsBatch` for the cascade). Notes on the non-obvious behavior:

- **`create_menu` defaults.** `days` (default 1) and `notes` (default "") are `.optional().default(...)` on the input schema AND re-defaulted in the handler (`args.days ?? 1`, `args.notes ?? ""`) so the handler is robust to direct invocation that bypasses the SDK's Zod parse (the test harness's `callTool` does not apply schema defaults). `orderFlag` is `max(existing orderFlags) + 1` so the new menu sorts last in Paprika order. Duplicate guard mirrors `create_grocery_list`: only an exact case-insensitive name match rejects; a starts-with/contains `findByName` hit does not.
- **`update_menu` days-shrink guard.** Resolves the menu via `resolveLookup` (uid or tiered fuzzy name), then — when `days` is supplied — refuses to lower it below the highest `day` among the menu's live menuitems (`menuItemStore.getByMenuUid`), enumerating the conflicting recipes (name + day) and saving nothing. This prevents orphaning menuitems on days that fall outside the new span. When `name` is supplied, also rejects a rename whose target collides with a different menu (case-insensitive exact match via `findByName`, excluding the menu's own UID — mirrors `create_menu` and `rename_grocery_list`); a no-op rename to the menu's own current name falls through. Otherwise it partial-merges name/days/notes onto the existing menu. Requires at least one of name/days/notes; an empty payload short-circuits with "Nothing to update."
- **`delete_menu` cascade.** Resolves the menu, then tombstones every menuitem (`{...item, deleted: true}`) in a single `saveMenuItems` + `commitMenuItemsBatch` FIRST (children before parent), then tombstones the menu via `saveMenus` + `commitMenu`. The children-first ordering means a parent-delete failure leaves orphaned-but-visible items the next sync can reconcile rather than a parent with invisible children (same rationale as `move_to_pantry`). On a cascade-item failure the menu is NOT touched; on a menu-save failure after the items are gone, the message notes the items were deleted and the next sync should reconcile the menu.

### `menu-item-write.ts`

Exports `registerAddMenuItemsTool`, `registerUpdateMenuItemTool`, and `registerDeleteMenuItemTool`, plus `addMenuItemsInputSchema` / `updateMenuItemInputSchema` / `deleteMenuItemInputSchema` for direct Zod-validation tests. All three menuitem write tools live in one file, mirroring `grocery-item.ts`'s add/update/delete trio. The `type` field reuses `mealTypeSpecSchema` + `resolveMealTypeSpec` from `meal-helpers.ts` — menuitems link to meal types exactly like meals do. Notes on the non-obvious behavior:

- **`add_menu_items` batch + recipe-XOR-freeform.** Resolves the parent menu (single — uid or tiered fuzzy name via `resolveLookup`; misses/ambiguity short-circuit with the standard wording). Each item is a `z.union` of two `.strict()` shapes (like `add_meals`): **recipe-linked** (`recipe_uid` must be in `ctx.store` (RecipeStore) so the display `name` denormalizes off `recipe.name`) OR **freeform** (`name`, no `recipe_uid` — stored as `recipeUid: null` with the supplied name, materialized as-is by `add_menu_to_planner`). Supplying both `recipe_uid` and `name` matches neither strict variant and is rejected at the Zod boundary. Stage 1 collects ALL per-index errors (unknown recipe / unknown type), prefixed `Item ${i}:`, and rejects the whole batch if any fail.
- **`add_menu_items` AUTO-EXPAND.** `maxDay` = highest `day` across the batch; when `maxDay > menu.days` the handler builds an extended menu (`days = maxDay`), `saveMenus([extended])` + `commitMenu` **FIRST**, then adds the items — so no menuitem ever references a day outside a saved menu. The success header notes the extension. (This overrides the rejected "day must be ≤ menu.days" alternative.)
- **`add_menu_items` menu-wide order_flag.** Assigns `orderFlag` as a single **menu-wide** sequence — seeded from the highest existing live-item `orderFlag` across the _whole_ menu (`getByMenuUid`, `+1`), then `seed + idx` per batch item in submission order, regardless of day. This matches the Paprika wire capture: a multi-day menu's day-1 item is `order_flag: 0` and its day-3 item is `order_flag: 1` (`docs/wire-captures/menus.har.json`), i.e. NOT reset per day. UIDs are uppercase UUID v4 (`MenuItemUidSchema.parse(crypto.randomUUID().toUpperCase())`). Built items POST in one `saveMenuItems` + `commitMenuItemsBatch`.
- **`update_menu_item` partial-merge.** Requires ≥1 of `day` / `type` / `recipe_uid` (empty → "Nothing to update."). Re-resolves `type` → `typeUid` via the shared helper; a new `recipe_uid` refreshes both `recipeUid` and the denormalized `name` from RecipeStore (rejects an unknown recipe). `menu_uid` is intentionally not editable. **Day moves** (when `day` is supplied): if the new `day` exceeds the parent menu's span, the menu is auto-extended (`saveMenus([{…, days: newDay}])` + `commitMenu`, committed BEFORE the item) so the moved item stays visible in `menuToMarkdown` (which renders only Day 1..`menu.days`) — mirrors `add_menu_items`; and when the day actually changes, `orderFlag` is re-sequenced to the **menu-wide** max+1 (over all the menu's items, excluding this one) — order_flag is menu-wide per the wire capture, so this places the moved item last and keeps flags unique. Both are skipped for an orphaned item (`menuUid` null) or a menu not in the local store. Three-tier miss detection (tombstone vs never-existed vs already-`deleted`), then `saveMenuItems([merged])` + `commitMenuItem`.
- **`delete_menu_item` idempotency.** Tombstones the item (`{...item, deleted: true}`) via `saveMenuItems` + `commitMenuItem`; a retried delete returns "already deleted" from the store's tombstone set without re-POSTing (same shape as `delete_grocery_item` / `delete_meal`).

## Testing (`tool-test-utils.ts`)

Shared test utilities for direct tool handler invocation without a real MCP server.

- **`makeTestServer()`** -- Returns a stub `McpServer` that captures tool and resource handlers. Exposes `callTool(name, args)`, `callResourceList(name)`, `callResource(name, uid)`, and a `sendResourceListChanged` spy on the server stub itself. **Note:** `commitRecipe` routes resource-list notifications through `ctx.notifier` instead of `ctx.server.sendResourceListChanged()`. Tests asserting on commit-path notifications should spy on the notifier (see `makeStubNotifier()` below); the `makeTestServer().sendResourceListChanged` spy only fires for direct `server.sendResourceListChanged()` calls, which are no longer made from helper code. `commitPantryItem` does not emit `resourceListChanged` — pantry items have no resource surface.
- **`makeStubNotifier()`** -- Returns `{ notifier, resourceListChanged, loggingMessage }`. The `notifier` satisfies the `Notifier` interface and is wired with `vi.fn()` spies; assert on the returned spies (e.g. `expect(resourceListChanged).toHaveBeenCalledTimes(1)`). Pass `notifier` into `makeCtx(..., { notifier })` for any test that exercises `commitRecipe`/`SyncEngine` notification behavior.
- **`makeCtx(store, server, overrides?)`** -- Creates a minimal `ServerContext` with a real `RecipeStore` and stub `client`/`cache`/`pantryStore`/`vectorStore`/`notifier`. Overrides accept `client`, `cache`, `pantryStore`, `vectorStore`, and `notifier`. Write-tool tests pass `{ client, cache }` with mocked `saveRecipe`/`notifySync` and a nested cache mock like `{ recipes: { put }, flush }` (or `{ pantry: { put, remove }, flush }`) cast to `DiskCacheRoot`, plus a `notifier` from `makeStubNotifier()` when asserting on notifications. If no `notifier` is provided, a no-op notifier is used. `vectorStore` defaults to `null`.
- **`getText(result)`** -- Extracts the text string from a `CallToolResult`.

## Boundaries

- Tool handlers **must not** import client or cache modules from `paprika/` or `cache/` at runtime -- access data through `ctx.store` and `ctx.client` on `ServerContext`.
- Runtime imports of **Zod schemas** from `paprika/types.js` are allowed (e.g., `RecipeUidSchema` for input validation at tool boundaries).
- `import type` from `paprika/` and `cache/` is allowed (no runtime footprint).
- Runtime imports from `utils/` are allowed (cross-cutting utilities, e.g., `parseDuration`).
