# OAuth 2.1 Authentication for HTTP Transport Design

## Summary

mcp-paprika is a Paprika recipe manager MCP server that adds a spec-compliant OAuth 2.1 authentication layer to its HTTP transport. The architectural shape is an _issuer-with-OIDC-delegation_ model: the server acts as a full OAuth 2.1 authorization server toward MCP clients (such as claude.ai), while identity verification is entirely delegated to a single, operator-configured upstream OIDC provider — Google, Entra, Okta, Auth0, or Keycloak, selected via a preset or a raw discovery URL. This two-layer design keeps the layers isolated: the upstream IdP handles login and issues an id_token; the server validates that id_token against an operator-defined allowlist (`MCP_ALLOWED_EMAILS` / `MCP_ALLOWED_SUBS`), then mints its own opaque access and refresh tokens. claude.ai never sees an upstream token; the upstream never sees a claude.ai `client_id`.

The implementation is built on `@hono/mcp`'s `mcpAuthRouter`, which handles well-known metadata endpoints and standard token-endpoint plumbing. A custom `MintingOAuthServerProvider` (in `src/auth/provider.ts`) implements the `OAuthServerProvider` interface from `@modelcontextprotocol/sdk` — owning the full token lifecycle rather than delegating to a `ProxyOAuthServerProvider` — and composes the stores, OIDC client, and allowlist checker defined in `src/auth/`. Opaque tokens, DCR'd clients, and their hashed secrets are persisted through an additive extension of the existing `DiskCache`, following the same namespace-per-feature pattern used by pantry data. The design follows the project's established Functional Core / Imperative Shell structure and uses `neverthrow` `Result` types throughout the pure modules.

## Definition of Done

**Primary deliverable.** A spec-compliant OAuth 2.1 authentication layer for the `MCP_TRANSPORT=http` path, where this server acts as the OAuth issuer to MCP clients (e.g. `claude.ai`) while identity is delegated to a single configured upstream OIDC IdP (Google, Entra, Okta-family — selected via a `MCP_OIDC_PRESET` env var, or via raw `MCP_OIDC_DISCOVERY_URL`). Built on `@hono/mcp@0.2.5`'s `mcpAuthRouter` mounting a custom `OAuthServerProvider` (implementing the `@modelcontextprotocol/sdk` interface directly, not via `ProxyOAuthServerProvider`, because we mint and own our access/refresh tokens rather than proxying upstream ones).

**Success criteria.**

1. **End-to-end claude.ai connector flow works** against at least one configured upstream (Google for the test path) — public-client registration via DCR (returns `client_id` + `registration_access_token`; no `client_secret` because the only supported `token_endpoint_auth_method` is `"none"` and PKCE is the client authentication), browser login, token issuance, and authenticated MCP tool calls.
2. **Endpoints implemented**: `/authorize`, `/token`, `/revoke` (RFC 7009), `/register` (RFC 7591), `/register/{client_id}` (RFC 7592 PUT/DELETE), `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`, plus an `/oauth/callback` for the upstream IdP redirect leg. PKCE-S256 enforced; `resource` audience binding (RFC 8707) enforced; `iss` advertised on auth responses (RFC 9207).
3. **Authorization gate** admits identities listed in `MCP_ALLOWED_EMAILS` (subject to per-preset `email_verified` policy; default _strict_) or in `MCP_ALLOWED_SUBS`; everyone else gets 401. At least one list must be non-empty or the server refuses to start in HTTP mode.
4. **Persistence**: opaque access tokens, refresh tokens, DCR'd clients, and their RFC 7592 registration access tokens (hashed) survive process restart via DiskCache. Auth-code state is in-memory with TTL.
5. **DCR hygiene**: rate-limit on `POST /register` (10/hour per IP), hard cap on registered-client count (~50, returning 429 above), background cleanup task expiring stale clients (no token activity in 90 days).
6. **Issuer URL** sourced from `MCP_PUBLIC_URL`; HTTP transport refuses to start if it's missing or non-HTTPS.
7. **README updated** with the OAuth deployment walkthrough (registering an OIDC client in the upstream, env vars, allowlist setup); the "no built-in auth" warning is removed from the HTTP-transport section.

**Out of scope.** GitHub or other non-OIDC upstreams; Client ID Metadata Documents (CIMD); a `/logout` endpoint distinct from `/revoke`; admin UI / dashboards; per-user upstream provider configs; signed JWTs as token format; multi-issuer support; bulk-revoke-by-identity; rotating signing keys or JWKS.

## Acceptance Criteria

### oauth21-http.AC1: claude.ai connector end-to-end flow

- **oauth21-http.AC1.1 Success:** `POST /register` from a claude.ai-shape request returns 201 with `client_id` + `registration_access_token` in plaintext (returned exactly once; no `client_secret` is issued — we are a public-client-only OAuth server).
- **oauth21-http.AC1.2 Success:** Full `/authorize` → upstream IdP stub → `/oauth/callback` → `/token` chain completes end-to-end and returns a usable access + refresh token pair.
- **oauth21-http.AC1.3 Success:** `POST /mcp` with `Authorization: Bearer <access_token>` reaches the MCP handler and the call succeeds; `AuthInfo.extra` carries `email`, `sub`, `source`.
- **oauth21-http.AC1.4 Success:** `POST /token` with `grant_type=refresh_token` rotates the refresh token: returns a new pair, the old refresh token returns `invalid_grant` on next use.
- **oauth21-http.AC1.5 Failure:** `POST /mcp` without `Authorization` header returns 401.
- **oauth21-http.AC1.6 Failure:** `POST /mcp` with malformed/expired/unknown token returns 401 with generic body (no token-detail leakage).

### oauth21-http.AC2: OAuth endpoint surface

- **oauth21-http.AC2.1 Success:** `GET /.well-known/oauth-authorization-server` returns RFC 8414 metadata; `issuer` matches `MCP_PUBLIC_URL` exactly (passed as string, not `URL` object, to avoid trailing-slash normalization); `code_challenge_methods_supported = ["S256"]`; no `id_token_signing_alg_values_supported` field; `token_endpoint_auth_methods_supported = ["none"]` exactly (public-client only — the library default of `["client_secret_post"]` is overridden); `authorization_response_iss_parameter_supported = true` (added to the library's default metadata to advertise RFC 9207 support).
- **oauth21-http.AC2.2 Success:** `GET /.well-known/oauth-protected-resource` returns RFC 9728 metadata; `resource = MCP_PUBLIC_URL`; `authorization_servers` includes the issuer URL.
- **oauth21-http.AC2.3 Success:** `GET /authorize?...` redirects (302) to the upstream `/authorize` URL with chained state, nonce, and PKCE forwarded.
- **oauth21-http.AC2.4 Success:** `POST /token` with `grant_type=authorization_code` and valid PKCE returns `{access_token, refresh_token, expires_in: 86400, token_type: "Bearer", scope}`.
- **oauth21-http.AC2.5 Success:** `POST /revoke` removes the token from storage and returns 200; subsequent `/mcp` calls with that token return 401.
- **oauth21-http.AC2.6 Success:** `POST /register` returns 201 with full RFC 7591 client metadata (without `client_secret`/`client_secret_expires_at` — those fields are absent for public clients) plus our additions: `registration_access_token` and `registration_client_uri` (the URL the client uses for RFC 7592 management, equal to `MCP_PUBLIC_URL/register/{client_id}`).
- **oauth21-http.AC2.7 Success:** `PUT /register/{client_id}` with correct `registration_access_token` updates the client's metadata; response is 200 with the full client information document including the current `registration_access_token` and `registration_client_uri` (per RFC 7592 §2.2).
- **oauth21-http.AC2.8 Success:** `DELETE /register/{client_id}` with correct RAT removes the client AND cascades to all tokens issued for that `clientId`; response is 204 No Content (per RFC 7592 §2.3).
- **oauth21-http.AC2.9 Failure:** `GET /authorize` without `code_challenge` returns `invalid_request` (per OAuth 2.1).
- **oauth21-http.AC2.10 Failure:** `POST /token` with `resource` not matching the original `/authorize`'s `resource` returns `invalid_target` (per RFC 8707 §2). Same error for any refresh-token exchange that requests a `resource` not bound to the original grant.
- **oauth21-http.AC2.11 Failure:** `POST /token` with an already-consumed auth code returns `invalid_grant` (single-use).
- **oauth21-http.AC2.12 Failure:** `PUT/DELETE /register/{client_id}` without or with wrong `registration_access_token` returns 401.
- **oauth21-http.AC2.13 Failure:** No published metadata document advertises `alg=none` anywhere; no PKCE method other than `S256` is offered.
- **oauth21-http.AC2.14 Success:** `/oauth/callback` redirects back to claude.ai's `redirect_uri` include `iss=<MCP_PUBLIC_URL>` (RFC 9207). Applies to both success redirects (with `code` and `state`) and error redirects (with `error` and optional `error_description`).

### oauth21-http.AC3: Authorization gate (allowlist + email_verified policy)

- **oauth21-http.AC3.1 Success:** id_token with `email = "user@x"` and `email_verified = true` where `"user@x" ∈ MCP_ALLOWED_EMAILS` → admitted with `source = "email"`.
- **oauth21-http.AC3.2 Success:** id_token with `sub = "sub-1"` where `"sub-1" ∈ MCP_ALLOWED_SUBS` → admitted with `source = "sub"` (regardless of email or `email_verified`).
- **oauth21-http.AC3.3 Success:** id_token matching both email and sub allowlists → admitted (OR semantics); `source = "email"` (email-precedence convention).
- **oauth21-http.AC3.4 Failure:** id_token whose email is not in `MCP_ALLOWED_EMAILS` and whose sub is not in `MCP_ALLOWED_SUBS` → callback fails with OAuth-shaped error; no token issued; identity logged at warn level but token never logged.
- **oauth21-http.AC3.5 Failure:** id_token with allowlisted email but `email_verified = false` and policy `strict` (default) → denied with `OAuthAllowlistDenialError`.
- **oauth21-http.AC3.6 Success:** id_token with allowlisted email and `email_verified = false` and policy `skip` → admitted.
- **oauth21-http.AC3.7 Edge:** id_token with allowlisted email, `email_verified` claim absent, policy `strict` → denied.
- **oauth21-http.AC3.8 Edge:** id_token with allowlisted email, `email_verified` claim absent, policy `if-present` → admitted.
- **oauth21-http.AC3.9 Failure:** HTTP-transport server with `MCP_ALLOWED_EMAILS` and `MCP_ALLOWED_SUBS` both empty refuses to start (config validation fails fast).

### oauth21-http.AC4: Persistence across restart

- **oauth21-http.AC4.1 Success:** A DCR'd client persists across process restart; `registration_access_token_hash` is preserved (there is no `client_secret_hash` because we issue no `client_secret`).
- **oauth21-http.AC4.2 Success:** An issued access token persists across restart; lookup returns valid `AuthInfo` post-restart.
- **oauth21-http.AC4.3 Success:** An issued refresh token persists across restart; rotation works post-restart.
- **oauth21-http.AC4.4 Success:** Auth codes do NOT persist across restart (in-memory only); restart mid-flow invalidates outstanding codes.
- **oauth21-http.AC4.5 Success:** Inspecting on-disk JSON for an OAuth client shows `registrationAccessTokenHash` as a 64-character hex string; no plaintext present (client records contain no `client_secret` at all because the server is public-client only).
- **oauth21-http.AC4.6 Success:** Inspecting filenames in `oauthTokens/`: each file name is exactly `<sha256_hex>.json`; the file's `tokenHash` field equals the filename's hex.

### oauth21-http.AC5: DCR operational hygiene

- **oauth21-http.AC5.1 Success:** 10 `POST /register` requests from the same IP within a 1-hour window succeed; the 11th returns 429.
- **oauth21-http.AC5.2 Success:** With 50 registered clients, the next `POST /register` returns 429 with `error_description` indicating client cap.

## Glossary

- **MCP (Model Context Protocol)**: A protocol for exposing tools and resources from a server to an LLM client. This server implements MCP over stdio and HTTP transports.
- **OAuth 2.1**: A consolidated security profile of OAuth 2.0 that mandates PKCE for all clients, removes implicit and password-grant flows, and requires `https://` for redirect URIs. The superseding draft of RFC 6749.
- **OIDC (OpenID Connect)**: An identity layer on top of OAuth 2.0 that adds an `id_token` (a signed JWT) containing user identity claims such as `email`, `sub`, and `email_verified`. Used here for the upstream IdP leg.
- **PKCE (Proof Key for Code Exchange, RFC 7636)**: A mechanism that binds an authorization code to the client that requested it by requiring a `code_verifier` at the token endpoint. OAuth 2.1 mandates S256 only; this server enforces that via `@hono/mcp`.
- **DCR (Dynamic Client Registration, RFC 7591)**: Allows OAuth clients to register programmatically with an authorization server rather than through out-of-band admin steps. claude.ai uses DCR to obtain a `client_id` (and an RFC 7592 `registration_access_token`) from this server at connector setup time. Because this server is public-client only, no `client_secret` is issued.
- **RFC 7591**: Defines the Dynamic Client Registration protocol (`POST /register`).
- **RFC 7592**: Defines the Dynamic Client Registration Management protocol (`GET/PUT/DELETE /register/{client_id}`), allowing clients to read, update, or delete their own registration.
- **RFC 7009**: Defines the token revocation endpoint (`POST /revoke`).
- **RFC 8414**: Defines the OAuth Authorization Server Metadata discovery document format, served at `/.well-known/oauth-authorization-server`.
- **RFC 8707**: Defines the `resource` parameter for audience-binding tokens to a specific protected resource, preventing token substitution attacks.
- **RFC 9207**: Defines the `iss` (issuer) response parameter on authorization endpoint responses, allowing clients to detect mix-up attacks.
- **RFC 9728**: Defines the OAuth Protected Resource Metadata discovery format, served at `/.well-known/oauth-protected-resource`.
- **JWKS (JSON Web Key Set)**: A JSON document advertising a set of public keys used to verify signed JWTs. The upstream IdP exposes a JWKS endpoint; this server fetches it via jose's `createRemoteJWKSet` to verify id_tokens.
- **id_token**: A signed JWT issued by an OIDC provider containing the authenticated user's identity claims (`sub`, `email`, `email_verified`, `iss`, `aud`, `nonce`). This server validates id_tokens from the upstream IdP, then discards them and mints its own opaque tokens.
- **JWS / JWT**: JSON Web Signature / JSON Web Token. The id_token is a JWS-encoded JWT. This server uses jose's `jwtVerify` for verification. The server's own tokens are opaque (random bytes), not JWTs.
- **jose**: A TypeScript/JavaScript library for JOSE primitives (JWT, JWS, JWK, JWKS). Used here for id_token verification and remote JWKS fetching.
- **@hono/mcp**: A Hono integration package for the MCP SDK. Provides `mcpAuthRouter`, which mounts the OAuth well-known metadata documents, the DCR endpoint, and the standard `/authorize`, `/token`, and `/revoke` routes, delegating logic to an `OAuthServerProvider`.
- **mcpAuthRouter**: The Hono router exported by `@hono/mcp` that mounts the full OAuth surface (well-known docs, DCR, authorize, token, revoke). This server mounts it ahead of `/mcp` when `MCP_TRANSPORT=http`.
- **OAuthServerProvider**: The interface from `@modelcontextprotocol/sdk` that `mcpAuthRouter` calls into for authorization logic — `authorize`, `exchangeAuthorizationCode`, `exchangeRefreshToken`, `verifyAccessToken`, `revokeToken`, and `clientsStore`. Implemented here by `MintingOAuthServerProvider`.
- **ProxyOAuthServerProvider**: An `OAuthServerProvider` implementation in `@modelcontextprotocol/sdk` designed for servers that proxy an upstream OAuth server's tokens rather than minting their own. This server does _not_ use it — we mint and own our access/refresh tokens.
- **OAuthRegisteredClientsStore**: The interface within `OAuthServerProvider` for client storage — `getClient` and `registerClient`. Implemented by `client-registration.ts`, backed by `DiskCache`.
- **AuthInfo**: The shape returned by `verifyAccessToken` and attached to the request context by `bearerAuth` middleware. Contains `token`, `clientId`, `scopes`, `expiresAt`, `resource`, and an `extra` field carrying `email`, `sub`, and `source`.
- **MintingOAuthServerProvider**: The project's own `OAuthServerProvider` implementation in `src/auth/provider.ts`. Mints and owns opaque access and refresh tokens rather than proxying upstream ones.
- **ResolvedOAuthConfig**: A Zod-validated type in `src/auth/types.ts` representing the merged, fully-resolved OAuth configuration after preset expansion and env-var application.
- **AuthContext**: The assembled OAuth runtime object stored in `AppContext.auth`. Holds the provider, cleanup task, and resolved config. `null` when `transport === "stdio"`.
- **AuthCleanup**: The background task in `src/auth/cleanup.ts` that expires stale DCR'd clients (those with `lastTokenActivityAt` older than 90 days) and cascades their token deletion. Mirrors the `SyncEngine` lifecycle pattern.
- **MCP_PUBLIC_URL**: The env var that sets the canonical HTTPS URL of this server, used as the OAuth issuer URL in all metadata documents and token responses. Required in HTTP mode; must be `https://`.
- **MCP_ALLOWED_EMAILS / MCP_ALLOWED_SUBS**: Env vars defining the identity allowlist. Only identities matching at least one entry (email or sub) in the respective list are admitted. At least one must be non-empty for the server to start in HTTP mode.
- **opaque token**: A token that is a random, structureless string with no embedded claims — as opposed to a JWT. Looked up on the server side (hash → stored record) to resolve identity and expiry.
- **registration_access_token**: A secret issued once at DCR time, required for all subsequent RFC 7592 management operations (`PUT/DELETE /register/{client_id}`). Stored hashed; returned in plaintext exactly once in the 201 response.
- **DiskCache**: The project's existing atomic-write, append-friendly file-system cache layer in `src/cache/disk-cache.ts`. Extended with two new namespaces (`oauthClients/`, `oauthTokens/`) to persist OAuth clients and tokens across process restarts.
- **AppContext**: The process-wide shared state object in `src/server/app-context.ts`, extended here with `auth: AuthContext | null` — `null` for stdio transport.
- **SyncEngine**: The existing background task in the project (Paprika sync loop) whose `start()` / `stop()` / `AbortController` / never-throws lifecycle contract `AuthCleanup` mirrors.
- **FCIS (Functional Core, Imperative Shell)**: The architectural pattern used throughout this project. Pure modules with no I/O (`tokens`, `allowlist`, `dcr-validator`, `presets`) form the core; modules that perform I/O (`oidc-client`, `client-registration`, `token-store`, `provider`, `routes`, `cleanup`) form the shell.
- **neverthrow Result**: The `Result<T, E>` type from the `neverthrow` library. Used for fallible operations in the functional core; callers use `.match()`, `.andThen()`, `.map()`, `.mapErr()` — never `.isOk()`/`.isErr()` imperative checks.
- **allowlist**: The operator-defined set of permitted identities, expressed as email addresses (`MCP_ALLOWED_EMAILS`) and/or subject identifiers (`MCP_ALLOWED_SUBS`). Admission uses OR semantics — matching either list is sufficient.
- **presets (Google / Entra / Okta / Auth0 / Keycloak)**: Named configurations in `src/auth/presets.ts` that supply the OIDC discovery URL, scope list, `email_verified` policy, and allowed signing algorithms for each supported upstream IdP, selected via `MCP_OIDC_PRESET`.
- **hono-rate-limiter**: A rate-limiting middleware for Hono, used to enforce the 10-registrations-per-hour-per-IP limit on `POST /register`.

## Architecture

### Two-layer OAuth model

Two distinct OAuth relationships are at play:

```
┌──────────┐    OAuth #1     ┌──────────────────┐    OAuth #2    ┌────────┐
│ claude.ai│ ◀──────────────▶│   our MCP server │◀──────────────▶│ Google │
│ (client) │                 │  (BOTH issuer    │                │ (IdP)  │
└──────────┘                 │   AND client)    │                └────────┘
                             └──────────────────┘
```

**OAuth #1 — claude.ai ↔ our server.** This is where the MCP spec applies and where Dynamic Client Registration lives. claude.ai POSTs `/register` to _our_ server, dynamically obtaining a `client_id` + `registration_access_token` (no `client_secret` — we are public-client only; `token_endpoint_auth_method = "none"` and PKCE-S256 is the client authentication). claude.ai hits _our_ `/authorize` with PKCE and receives an opaque access token at _our_ `/token`. PKCE, `resource` audience binding (RFC 8707), refresh, `/revoke`, and `iss`-on-redirect (RFC 9207) all live at this layer.

**OAuth #2 — our server ↔ upstream IdP.** A statically pre-registered OAuth client. We register _one_ OAuth client manually in the upstream IdP (Google Cloud Console, Entra app registration, etc.), once per deployment. The static credentials are env vars (`MCP_OIDC_CLIENT_ID`, `MCP_OIDC_CLIENT_SECRET`). When a user authenticates through OAuth #1, our server initiates OAuth #2 on their behalf: redirects to the upstream `/authorize`, exchanges the code at the upstream `/token`, and validates the resulting id_token (signature, audience, `email_verified`, allowlist). Once the upstream identity is verified, we mint a fresh opaque token in OAuth #1.

The two layers are isolated: claude.ai never sees an upstream token, the upstream IdP never sees a claude.ai client_id. The MCP spec's DCR requirement applies only at OAuth #1; the upstream IdP doesn't need to support DCR.

### Module layout

A new `src/auth/` module houses the OAuth surface, following the project's convention of subdirectory-per-feature-area.

```
src/auth/
├── CLAUDE.md
├── types.ts                  — Zod schemas + types: OAuthClient, AccessToken,
│                              RefreshToken, AuthCodeState, OAuthAuthInfoExtra,
│                              OIDC preset schema, ResolvedOAuthConfig

│                              OAuthClientNotFoundError, OAuthAllowlistDenialError,
```

### Token flow

Custom `OAuthServerProvider` mints opaque tokens on each token-endpoint exchange. The full sequence:

1. `/.well-known/oauth-authorization-server` + `/.well-known/oauth-protected-resource` served by `@hono/mcp`'s well-known router.
2. `POST /register` (DCR) — `clientsStore.registerClient` validates metadata via `dcr-validator` (must include `token_endpoint_auth_method = "none"`), accepts the library-generated `client_id` (UUIDv4), generates a `registration_access_token`, persists the hashed RAT in the client record, and returns the plaintext RAT plus `client_id` and `registration_client_uri` once in the 201 response. No `client_secret` is issued.
3. `GET /authorize` — `provider.authorize` stashes `{client_id, code_challenge, code_challenge_method, redirect_uri, resource, claude_state, scope, our_nonce}` in the **auth-request store** (in-memory; 5-minute TTL) keyed by a fresh `our_state`, then redirects to the upstream `/authorize` with our static `MCP_OIDC_CLIENT_ID`/`MCP_OIDC_CLIENT_SECRET` credentials, our `state`, and our `nonce`. PKCE is NOT chained to upstream — claude.ai's `code_verifier` never reaches our server until step 6, so we can't forward it. The OAuth #2 leg uses our confidential client_secret for authentication; PKCE applies only at OAuth #1 (claude.ai ↔ us).
4. Browser ↔ upstream IdP consent flow.
5. `GET /oauth/callback?code=upstream_code&state=our_state` — our custom handler looks up the **auth-request store** entry by `our_state`, exchanges `upstream_code` at the upstream `/token` (using our static client credentials), verifies the id*token (jose with `algorithms: ["RS256", "ES256"]`), checks `email_verified` per policy and allowlist match, mints our auth code (`mcp_ac*<base64url>`), and writes a new entry to the **auth-code store** (in-memory; 60-second TTL) keyed by `our_auth_code`carrying`{client_id, code_challenge, code_challenge_method, redirect_uri, resource, scope, identity}`. The auth-request-store entry is then deleted (single use). Redirects to claude.ai's `redirect_uri`with`code=our_auth_code`, `state=<claude.ai's original state from the auth-request record>`, and `iss=<MCP_PUBLIC_URL>` (RFC 9207).
6. `POST /token` (grant_type=authorization_code) — library calls `challengeForAuthorizationCode` (we return the stored `code_challenge`), library verifies PKCE, then calls `exchangeAuthorizationCode`. We consume the auth code (single-use), validate `redirect_uri` and `resource` match the stored values, mint access + refresh tokens, persist hashed records to DiskCache, return plaintexts in the response.
7. `POST /mcp` (Bearer mcp*at*…) — `bearerAuth` middleware calls `verifyAccessToken`. We SHA-256-hash the presented token, look up `oauthTokens/<hash>.json`, return `AuthInfo` with identity in `extra`.
8. `POST /token` (grant_type=refresh_token) — `exchangeRefreshToken(client, refreshToken, scopes?, resource?)` receives requested scopes and resource from the library; hash + lookup refresh token; validate requested `resource` matches the original grant's `resource` (else `invalid_target`) and requested `scopes` is a subset of the original grant's `scope` (else `invalid_scope`); invalidate the old refresh token immediately; mint a new pair with `rotatedFromHash` audit linkage and the (possibly narrowed) scope.
9. `POST /revoke` — `revokeToken` hashes and deletes; always returns 200 (no existence leak).
10. `PUT/DELETE /register/{client_id}` — custom routes verify the bearer `registration_access_token` via hash-and-lookup; PUT updates client metadata (re-validated through `dcr-validator`); DELETE removes the client and cascades to all tokens with matching `clientId` via `token-store.removeAllForClient`.

### Cryptography

The full ~35-invariant policy is documented in `src/auth/CLAUDE.md`. The load-bearing decisions:

- **No `alg=none`, ever.** jose's `jwtVerify` is always called with explicit `algorithms: ["RS256", "ES256"]` (or `oauth.allowedAlgs` if overridden). No HMAC algs accepted for id_token verification.
- **All upstream URLs must be `https://`.** Discovery docs that advertise `http://` for any endpoint are rejected at startup. Exception: DCR'd client `redirect_uris` allow `http://localhost*`.
- **All tokens are 32 bytes of CSPRNG entropy.** `crypto.randomBytes(32).toString("base64url")`. Prefixed for debug visibility (`mcp_at_`, `mcp_rt_`, `mcp_ac_`, `mcp_rat_`, `mcp_state_`, `mcp_nonce_` — no `mcp_cs_` because we issue no client secrets).
- **SHA-256-hashed at rest.** Plaintexts hit disk only as `hex(sha256(plaintext))`. Token files are keyed by hash, not plaintext. No `timingSafeEqual` anywhere because lookups never iterate.
- **PKCE S256 only.** `@hono/mcp` enforces. Metadata advertises `code_challenge_methods_supported: ["S256"]`.
- **No pepper** (HMAC keyed hash). Plain SHA-256 is sufficient for high-entropy random tokens. Documented escape hatch in `tokens.ts` for future tightening.

### Startup-time discovery fetch

`buildAuthContext` fetches the upstream OIDC discovery document and validates it at startup, before returning. A transient upstream IdP outage at boot blocks the server from starting. Accepted trade-off: there's no value in starting a server in HTTP mode that can't authenticate anyone, and fail-fast surfaces config problems immediately (rather than at first user login).

### Cascade-on-delete

Deleting a client via RFC 7592 DELETE (or via the cleanup task) cascades to all tokens with matching `clientId`. The cascade is one-directional: revoking a single token does _not_ cascade to other tokens for the same client. This matches OAuth 2.1 norms — `/revoke` is per-token; client deletion is per-identity.

### Concurrent cache writes (async mutex)

DiskCache's three-phase `flush()` (snapshot pending → write files → clear pending) was previously unsafe under concurrent `put*()` calls: a `put*` between snapshot and clear could land in `_index` without its file ever being written, and the final `clear()` could drop the un-snapshotted entry entirely. With sync-engine flushes (every 15min) and OAuth per-request flushes coexisting in one cache, this race is reachable.

Resolution: an internal async mutex on `DiskCache` (`_writeLock: Promise<void>`) serializes every method that mutates pending maps, `_index`, or performs `flush()`. Per-write OAuth writes call `flush()` immediately, which blocks until any in-flight Paprika flush completes; sync-engine batch writes serialize the same way. At our write rate (sync every 15min, OAuth a few writes per user session) the contention is negligible. The mutex implementation is ~20 LOC in `disk-cache.ts` (see Phase 3); the `src/cache/CLAUDE.md` invariants document this serialization guarantee.

### Future-cleanup notes

- **DiskCache type parameterization.** Currently DiskCache imports its entity schemas directly (`RecipeStoredSchema`, etc.). A future refactor could parameterize this — DiskCache becomes a generic atomic-write FS layer that accepts schema registrations at construction. Not worth doing as part of this work; noted for future consideration.
- **HMAC pepper.** The current design uses plain SHA-256 for token hashing. For a higher-threat-model deployment (or if this codebase ever migrates to a multi-tenant SaaS), adding a server-side pepper (via HMAC keyed by an env-var secret) raises the cost of file-system-leak attacks. The escape hatch is documented in `src/auth/tokens.ts` so future addition is a one-function change.
- **Signed JWTs as an alternative token format.** Opaque tokens were chosen for simplicity at this scale. A future migration to RS256-signed JWTs with a JWKS endpoint would be a non-trivial refactor (the persistence layer changes shape, key rotation policy needs design). Documented as out-of-scope for this work.
